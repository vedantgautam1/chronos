## Findings

### 1. BLOCKING — `content_hash` is not deterministic, and does not raise on unknown types used as dict keys

**File:** `v2/src/chronos2/core/canonical.py`, line 36 (`str(k): _canonical(v)`).

Dict **values** go through `_canonical`; dict **keys** go through bare `str()`. Keys are
therefore never validated and never canonicalised. Demonstrated [Certain — run]:

```
canonical_json({Thing(): 1})            -> {"<__main__.Thing object at 0x7f429e34d2b0>":1}
canonical_json({datetime(2026,4,1): 1}) -> {"2026-04-01 00:00:00":1}      # naive, no raise
canonical_json({float('nan'): 1})       -> {"nan":1}                      # NaN, no raise
```

Three separate processes, same input `{Thing(): 1}`:

```
c16f45e8a2569fbb
c079c2e0fd729f64
ec227604948deb45
```

**What the spec says.** Deliver item 4: "`canonical_json(obj) -> str` and
`content_hash(obj) -> str` … Raises on NaN, infinities, naive datetimes, sets, and
unknown types." That sentence is unqualified — it is a property of the function over its
input, not of values only. An object key, a naive-datetime key and a NaN key each reach a
hash instead of raising. The "Why" section states the module's purpose as "a stable
fingerprint of any piece of data"; for the object-key case the fingerprint embeds a memory
address and is different on every run.

Related, same root cause: `{1: "x", "1": "y"}` canonicalises to `{"1":"y"}` — one key is
**silently dropped**, no error.

**Why this is blocking rather than a note.** Everything later stands on this helper, and
the thing it is relied on for is exactly the thing that fails: the same input giving the
same hash. The failure is silent — no exception, no wrong-looking output, just a different
number next run. B09/B10/B11 hash trial payloads to detect a repeat look; a fingerprint
that drifts between processes would turn a duplicate trial into a new one, which is the
p-hacking the trial ontology exists to prevent. The spec chose "raises" over "best effort"
for precisely this reason, and no known-answer test covers keys, so nothing catches it.

**Suggested fix (builder's call, not mine to write):** route keys through the same
validation as values — either require `str`/`int` keys and raise `TypeError` otherwise, or
canonicalise the key and raise on anything that is not then a string — plus a known-answer
test for an object key, a naive-datetime key and the `{1:…, "1":…}` collision. Small and
contained in `_canonical`.

### 2. Note for the gate — floats, Decimals and strings share a fingerprint

`content_hash({"a": 1.0}) == content_hash({"a": Decimal("1.0")}) == content_hash({"a": "1.0"})`,
all canonicalising to `{"a":"1.0"}` [Certain — run]. This follows the spec as written
("floats by `repr`", "`Decimal` → its string"), so **the build is correct and this is not a
finding against the builder** — but it means the fingerprint cannot distinguish a number
from its string form. If a later build hashes a config where `"0.10"` and `Decimal("0.10")`
mean different things, it will not see a change. Worth a decision at the gate on whether
canonical values should be type-tagged.
