**1. BLOCKING — both jobs report `success` on GitHub even when the guards fail. The gate never turns red.**

*File and line:* `.github/workflows/v2-guards.yml:63` and `.github/workflows/v2-guards.yml:121`.

*What is wrong.* Each job ends its run step with `| tee <file>`. A GitHub `run:` step without an explicit `shell:` executes under `bash -e {0}`, which does **not** set `pipefail`, so the pipeline's exit status is `tee`'s — always 0. `run_all.py`'s non-zero exit is swallowed, and so is `earlier_tests`'s.

*The evidence, which is a real run and not a reconstruction.* Run `44412803088` on head `0c2999f`, the guards job:

```
Guards for claude/b02 -> v2-build
  11 commit(s), 20 path(s) changed
  ok    branch_kind
  ok    v1_frozen
  FAIL  scope  (2)
  FAIL  roles  (2)
  ok    frozen_files
  ok    plumbing
  ok    protected
4 finding(s). This pull request does not pass the guards.
```

and the step's own conclusion, from the jobs API: `step: Run the guards -> success`. The job conclusion is `success` and the pull request is mergeable. The same four findings exit 1 when I run the identical arguments locally, so the runner is right and the workflow discards its answer. I reproduced the mechanism directly: `bash -e -c 'bash failing.sh | tee out.txt'` exits **0**; adding `set -o pipefail` makes the same pipeline exit **1**.

*What the spec says.* Deliverable 1 is the gate itself; deliverable 2 requires `run_all.py` to exit "non-zero if any guard produces a finding", which it does — the workflow then throws that away. The `earlier-tests` Known answers are explicit that each trick must end "with the failing test still failing, **and the job red**". The job is not red. It cannot be red, for any input, today. Both jobs carry the defect, so every trick the spec lists as caught is in fact reported green on GitHub.

*Exact patch.* Two steps, same change in each.

`.github/workflows/v2-guards.yml`, the `Run the guards` step — as it is:

```yaml
      - name: Run the guards
        run: |
          bash v2/tools/guards/run_guards.sh \
```

as it should be:

```yaml
      - name: Run the guards
        shell: bash
        run: |
          set -o pipefail
          bash v2/tools/guards/run_guards.sh \
```

`.github/workflows/v2-guards.yml`, the `Run the earlier builds' tests against this branch's package` step — as it is:

```yaml
      - name: Run the earlier builds' tests against this branch's package
        run: |
          PYTHON="$(cd v2 && uv run python -c 'import sys; print(sys.executable)')"
```

as it should be:

```yaml
      - name: Run the earlier builds' tests against this branch's package
        shell: bash
        run: |
          set -o pipefail
          PYTHON="$(cd v2 && uv run python -c 'import sys; print(sys.executable)')"
```

The rest of both steps is unchanged, `| tee` included — `tee` is wanted, since the next step copies the file into the job summary. `shell: bash` and the explicit `set -o pipefail` do the same job twice on purpose: the first makes GitHub run the step under `bash --noprofile --norc -eo pipefail`, the second survives anyone later removing the `shell:` line.

*Also needed, and the builder should choose how.* Nothing in the suite would have caught this, and nothing in it would catch a regression. The workflow tests (`test_protected_and_workflow.py`) read the YAML for structure only — permissions, job names, absent strings. A cheap test in the same style: parse the YAML, and for every step whose `run` contains a pipe, assert the step either sets `shell: bash` or contains `set -o pipefail`. That is a text-and-structure check of the kind this build already does well, and it closes the class rather than the instance. **The founder should treat this as a spec gap too:** B02's Known answers never asked for "the workflow step fails when the runner fails", which is why a careful builder and a careful reviewer both missed it. B03's GitHub proofs should include one deliberately red run, observed on GitHub.

*Severity.* Blocking: the code is wrong, and it is wrong in the one way that matters most — the build's entire purpose is a gate that stops a bad branch, and this gate stops nothing. Everything else in B02 is sound, so this should be a small round.
