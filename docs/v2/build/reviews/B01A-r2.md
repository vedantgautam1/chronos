## Findings

### 1. BLOCKING, now corrected — the report asserted a founder decision that had not been taken

**File:** `docs/v2/build/reports/B01A.md`, "Deviations from the spec".

The paragraph read: *"flagged by the reviewer in B01A-r1; the founder chose to keep the
simpler form rather than revert."* Neither half was supportable from the repository
[Certain — run]:

- `docs/v2/build/reviews/B01A-r1.md` did not exist in **any** branch's history. The
  round-1 review was done in a chat session and its file was never committed.
- Nothing on the record showed the founder had decided to keep the simplified sort form.
  The founder's own account of round 1, given at the start of this round, listed the
  sort-line change as an open finding.

**Why this was blocking rather than a note.** The code defect B01A fixes is narrow — the
spec says it "may never have fired in practice". This is not narrow. B01A exists because a
build reviewed `CHANGES` was merged anyway and the project chose, explicitly, not to tidy
the record away: *"The record is not tidied away: `v2-build` carried a known defect from
`78298f3` until this build lands."* `specs/README.md` says in terms that the role checks
"can't catch a session that labels its commits falsely", and that what stands behind them
is the gate audit. CLAUDE.md rule 9: **only the founder locks decisions.** A build report
writing a founder approval into the permanent record defeats the one control this process
actually relies on, and it does it in the document written "for a non-technical reader
first". By this project's own standard that is worse than the bug.

**Correction made.** The sentence is replaced by a marked reviewer's note that states what
it previously said and why it was wrong, rather than deleted. **The founder made the
decision on 18 Nov: keep the simplified sort form.** That is now a real, dated decision
rather than an asserted one.

### 4. Note for the gate — the "determinism across processes" test cannot catch the defect it is named for

**File:** `v2/tests/core/test_canonical_keys.py`,
`test_content_hash_deterministic_across_processes`.

The spec calls this "the regression test for the actual defect". It hashes a
**string-keyed** dict, which was already deterministic under the buggy code — it passed at
step 1, before the fix [Certain — run]. It is a second wire-format pin, duplicating the
SHA-256 one; it is not a regression test for non-determinism. What actually closes that
hole is the six key tests, which make the non-deterministic input impossible.

**This is not a finding against the builder**: the spec prescribed this test and the build
implemented it exactly, and the spec was honest that it "passes already". The weakness is
in the spec. It matters because the report's plain-words paragraph leads with the
determinism story, so a non-technical reader would reasonably believe a test is standing
guard over it. If a later build widens the allowed key types, that is the moment to add a
real cross-process test using a key type that would have drifted.

### 5. Note for the gate — the sort inside `_canonical` is dead code, and the new form is less robust to a future widening

**File:** `v2/src/chronos2/core/canonical.py`, lines 38–41 and 65.

`canonical_json` calls `json.dumps(..., sort_keys=True)`, so the dict comprehension's
order never reaches the output. Removing the sort from `_canonical` entirely leaves all 31
tests green [Certain — run]. Both rounds of review have now spent time on a line that has
no effect — worth a note in `BUILD_NOTES.md` so the third reader does not repeat it.

Separately: `sorted(obj.items())` compares tuples, so it is safe **only** while every key
is a `str`. The spec's "Not in this build" explicitly contemplates a later build widening
the allowed key types to `int`, `Decimal`, `datetime` or `Enum`. On a mixed-type dict,
`sorted(obj.items())` raises `TypeError: '<' not supported between instances of 'str' and
'int'`, where B01's `key=lambda kv: str(kv[0])` would not have [Likely — reasoned, not
run]. Harmless today because non-`str` keys now raise before the sort. Whoever writes that
widening spec should know this line is load-bearing against it.

### 6. Note — round 1's review file was missing and has been reconstructed

`reviews/B01A-r1.md` now exists, written in this round and **marked unmistakably as a
reconstruction**, not as the round-1 reviewer's work. Its findings are as the founder
relayed them; the original evidence, line numbers and mutation results are lost. A gate
audit that found nothing there could not have distinguished a missing file from a review
that never happened.

The underlying cause is worth fixing: round 1 ran in a session without write access to the
repository, so its review could not be committed. Any review session must have push
access, or its findings die with the session.

Recorded so the next reviewer does not re-raise it.

## Role deviation — a reviewer edited builder files

The role table in `specs/README.md` lets the reviewer write `reviews/`, `status/` and
`LEDGER.md`. Correcting findings 1 and 2 meant editing `reports/B01A.md` and
`CHANGELOG.md`, both builder paths. **Done on the founder's explicit instruction of 18
Nov**, which is the only authority that makes it legitimate — CLAUDE.md rule 9, only the
founder locks decisions. Disclosed here so the gate audit sees a reviewer commit touching a
builder file and finds the reason rather than an anomaly.

The founder is locking a rule change that makes this ordinary in future: findings split
into blocking and non-blocking, with record-level corrections made by the reviewer rather
than costing a build round, and blocking findings carrying an exact patch for the builder
to apply. Had that rule been in force, B01A would have passed in one round.
