### 1. BLOCKING — `_halt_issues` finds halt issues by their *current* label, so the automation's own account can lift the emergency stop. Rows 30b and 30c are defeated through `gather()`.

*File and line:* `v2/tools/loop/facts.py:375-382` (`_halt_issues`), with `facts.py:211` and `facts.py:215` (`gather` calling it and passing the result to `halt_in_force`) as the second half of the mechanism.

*What is wrong.* `_halt_issues` asks GitHub for `issues?state=all&labels={label}`. That parameter filters on the labels an issue **currently carries** — GitHub documents it only as "A list of comma separated label names", with nothing about label history, and on this repository I confirmed the behaviour directly: 32 issues exist and every label-filtered query returns 0, because no issue currently carries a label. So:

- **row 30b**, the label removed from the issue by the automation's account → the issue is no longer returned → `halt_in_force([])` → `False`;
- **row 30c**, the label deleted from the repository → no issue carries it → `halt_in_force([])` → `False`.

`halt_in_force` is correct and would return `True` for both if it were handed the issue. It never is. The stop is lifted by exactly the actor the rule exists to exclude.

*Measured.* With an `api` stub that models the documented filter faithfully, comparing what `gather()` concludes against what the rule concludes from the same timeline:

```
row 30  -- automation CLOSED the issue, label still on it
  OK        issues found: 1   gathered: True    by the rule: True
row 30b -- automation REMOVED the label from the issue
  DEFEATED  issues found: 0   gathered: False   by the rule: True
row 30c -- label DELETED from the repository
  DEFEATED  issues found: 0   gathered: False   by the rule: True
```

Row 30 survives only because the label is still attached in that case. **All 278 tests pass with this defect present**, because no test exercises `_halt_issues` at all — the row tests hand the issues straight to `halt_in_force`.

*What the spec says.* Two places, both explicit. The fixed rules: "The script reads each issue's **timeline**, not its current labels. … It ends only when **the repository's owner** closes that issue or removes the label. If any other account closes the issue, **removes the label, or deletes the label from the repository**, the stop stays in force." And Deliver 2: `facts.py` must gather "`chronos-halt` issues and who closed them". The build reads the timeline faithfully once it has the issue, and then uses current labels to decide which issues it has. Rows 30b and 30c state `NONE` (still halted); the delivered system produces the opposite for the facts those rows state.

*Severity: blocking,* on two of the Severity block's grounds. A Deliver item is wrong — the collector cannot supply the set the rule needs. And two Known-answers rows have no test of the thing they state: their tests assert the rule in isolation, not the row, so they assert less than the spec states. This is not a weakness in the spec: the spec enumerates three ways the stop must survive and the build survives one. It is the same class as the two defects the builder found mid-build and fixed rather than disclosed, and the builder's own words for those apply unchanged — "a Deliver item half-built, not a gap in the spec."

*I considered and rejected the argument for non-blocking.* The spec does say the stop "is a guard rail, not a wall… enforced by this script, which the automation's own sessions run", and that the switches nothing can override are the founder's. That concedes a determined, deceptive session could get past it. It does not license the guard rail failing its own written rule on an ordinary label removal, which needs no deception at all. The `chronos-halt` label does not yet exist in the repository, so nothing is live today — but B04 drives this code and B05 runs it unattended, and the stop is the thing that stops them.

*Patch, verified.* `v2/tools/loop/facts.py`, as it is:

```python
def _halt_issues(api, repo: str, label: str) -> list[dict]:
    issues = api(f"issues?state=all&labels={label}&per_page=100", repo=repo) or []
    out = []
    for issue in issues:
        number = issue.get("number")
        timeline = api(f"issues/{number}/timeline?per_page=100", repo=repo) or []
        out.append({**issue, "timeline": timeline})
    return out
```

as it should be:

```python
def _halt_issues(api, repo: str, label: str) -> list[dict]:
    """Every issue the label was ever put on -- not every issue carrying it now.

    ``issues?labels=`` filters on an issue's *current* labels, so on its own it
    lets the automation's own account end a stop by removing the label, or by
    deleting the label from the repository: exactly what rows 30b and 30c
    forbid. The repository's issue-events feed names every ``labeled`` event
    with its label, so the union of the two gives the candidates whose
    timeline then decides.
    """
    candidates: dict[int, dict] = {}
    for issue in api(f"issues?state=all&labels={label}&per_page=100", repo=repo) or []:
        if issue.get("number") is not None:
            candidates[issue["number"]] = issue
    for event in api("issues/events?per_page=100", repo=repo) or []:
        if event.get("event") != "labeled":
            continue
        if ((event.get("label") or {}).get("name") or "") != label:
            continue
        number = (event.get("issue") or {}).get("number")
        if number is not None:
            candidates.setdefault(number, {"number": number})
    out = []
    for number in sorted(candidates):
        timeline = api(f"issues/{number}/timeline?per_page=100", repo=repo) or []
        out.append({**candidates[number], "timeline": timeline})
    return out
```

`GET /repos/{owner}/{repo}/issues/events` is REST, not GraphQL, as the spec requires, and it returns `event`, `label.name`, `issue.number` and `actor.login` — I called it against this repository and it works (72 events today). Keeping the `labels=` query as the other half of the union matters: it covers an issue whose events have aged out of the feed.

**Measured with the patch applied:** rows 30, 30b, 30c and 31 all agree with the rule, 4 of 4 where the shipped code manages 2 of 4; **278 passed**; `ruff check` clean. Reverted afterwards — the tree I reviewed is unmodified.

*The tests to add,* so the row is pinned at the layer that failed rather than only above it: give `_halt_issues` a stub api that filters on current labels, and assert that an issue whose label the automation removed is still gathered and still reads as a stop; same for the label deleted repository-wide. One test per row, both at the collector.

*And one thing to carry past this fix.* The two collector defects the builder found and this third one were all invisible to a 278-test suite for the same structural reason: every row test hands `decide()` or a pure helper its facts directly, so nothing anywhere asserts that `gather()` produces the facts the rows describe. The step 6 dry run is the only end-to-end pass and it stubs GitHub entirely, which is why it caught the `git`-side defect (`checks`) and neither API-side one. Worth a line in `BUILD_NOTES.md` and worth B04 having a row for.

### 2. NON-BLOCKING — `decide()` reads the system clock, so it is not the pure function Deliver 3 specifies. It cannot change an answer today; it is one new branch away from being able to.

*File and line:* `v2/tools/loop/next_action.py:174`, reached from `next_action.py:118` and `next_action.py:153,155`.

*What is wrong.* `_waiting_reason` calls `_for_gate(entry, ladder, facts, datetime.now(UTC))` instead of threading through the `now` that `decide()` was given. Deliver 3 specifies "**a pure function** `decide(ladder, facts, now) -> Action` with no I/O", and the module's own docstring says "It does no I/O at all."

*Measured, in both directions, because the first reading was wrong and the second is the honest one.* Replacing that line with a raise shows `decide()` **does** reach it on five tested rows — 1, 5, 6, 8 and 8b — so it is on the ordinary path for a gate waiting on the founder, not dead code. But holding `facts` and `now` fixed while moving the wall clock ten years in each direction, across all five of those rows and two more with a gate branch and a fresh and a stale lock, gives **byte-identical** `(kind, id, reason)` every time. The reason is structural: every path that reaches `_waiting_reason` with a gate returns from `_for_gate` before the `now` argument is consulted, because the three `WAIT_FOUNDER` branches all sit above the one `_fresh` call. So the clock is read and its value is discarded.

*What the spec says.* Deliver 3's "pure function… with no I/O" is not met in the strict sense. The Known-answers row that tests purity patches `subprocess` and `socket`, and `datetime.now` is neither, so the row passes as written — which is why this slipped through. It is also **not** the "local-time read" the Severity block calls blocking: it is `datetime.now(UTC)`, tz-aware, so CLAUDE.md's convention holds.

*Severity: non-blocking.* No Deliver item is behaviourally wrong, no known answer asserts less than the spec states, nothing is weakened, nothing is outside `touches` — and I verified the output cannot differ rather than assuming it. What makes it worth a finding rather than a note is that the protection is accidental: add one `WAIT_FOUNDER` branch below `next_action.py:301` and `decide()` becomes non-deterministic, with no test able to see it. B04 and B05 are the builds that would do that.

*Patch, verified, offered although rule 7 does not require one here.* Thread `now` through: give `_waiting_reason` and `_for_parked_or_start` a `now: datetime` parameter, pass `now` at the three call sites (`:96`, `:118`, `:153/:155`), and make `:174` read `_for_gate(entry, ladder, facts, now)`. **Applied locally: 278 passed, ruff clean**, and afterwards the only `datetime.now(UTC)` left in the module is in `main()`, which is the I/O boundary and is where it belongs. Reverted. Worth a test the spec does not have: `decide()` called twice with the same arguments under two different wall clocks returns equal Actions.

### 3. NON-BLOCKING — `facts._locks` reports a lock with no age when the clone has no remote-tracking ref for it; it fails open where `lock.is_stale` fails closed. Defended in depth, so it costs a wasted action rather than a double build.

*File and line:* `v2/tools/loop/facts.py:221-232`, specifically `facts.py:226`.

*What is wrong.* `gather` discovers lock references with `git ls-remote --heads origin`, which queries the **remote**, then `_locks` reads each one's date with `git log -1 … refs/remotes/origin/<name>`, which reads the **local** clone. A lock created after the clone last fetched is therefore listed but unreadable: `_git` returns `""` on failure, `_when("")` returns `None`, and the lock is reported with `lock_at=None`. `_fresh(None, …)` is `False`, so a lock that is in fact fresh reads as not fresh and `decide()` returns `RESUME_BUILD` or `REVIEW`.

*Measured with real git,* not a stub: a bare repository, a clone, then a `lock/b06` reference pushed to the bare repository after the clone.

```
ls-remote reports:        ['lock/b06', 'v2-build']
refs/remotes/origin/lock/b06:  fatal: unknown revision
_locks returns:           {'B06': (None, '')}
_fresh(None) would be:    False   -> reads as NOT fresh
```

*Why it is not blocking, and the reason is to this build's credit.* The decision is not where the lock is enforced. `Lock.take_over` reads the reference through the GitHub API, calls `is_stale`, and `is_stale` **raises** rather than returning `False` when it cannot read the age — "a lock the loop cannot judge is left alone, because treating it as free is the one answer that lets two sessions run at once", with a test pinning it. So the sequence is: `decide()` says resume, the agent calls `take_over`, the API says the real lock is fresh, `take_over` returns `False`. A wasted tick and a misleading status report, not two sessions building the same thing. The spec's own "check before every push" goes through the same API path. This is defence in depth working, and the inconsistency is worth recording precisely because the two modules answer the same question with opposite failure directions.

*What the spec says.* Deliver 2 asks for "lock references and their ages". It does not say `gather` fetches, so there is no stated rule this contradicts — it is a gap of the same kind the Severity block calls a weakness in the spec rather than the build.

*Cheapest fix for whichever build next touches this folder:* have `gather` fetch the lock references before reading them (`git fetch --no-tags origin '+refs/heads/lock/*:refs/remotes/origin/lock/*'`), or read the age through `GitHubRefs` as the lock itself does, or — at minimum — make `_locks` distinguish "no lock" from "a lock whose age I could not read" and have `decide()` treat the second as not-stale, matching `is_stale`.
