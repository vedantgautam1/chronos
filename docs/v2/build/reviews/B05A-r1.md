### 3. Every `!` porcelain line is read as a lost race, including a refusal by a GitHub rule — **non-blocking (spec weakness; for the gate)**

**Where:** `v2/tools/loop/lock.py`, `GitPushRefs._push`, the `if line is not None and line.startswith("!")` branch.
**What is wrong:** the code does what the spec says, and the report states the choice. But a push that a **ruleset or server hook** refuses also comes back flagged `!`, as `[remote rejected] (… declined …)`, so `create` returns `False`. Then `claim` prints "claimed, nothing to do" (another session holds it), while `next_action` sees no lock. If a rule ever covers `lock/*`, the loop would quietly do nothing on every tick. That is the "silent" failure this build exists to remove, moved from release to acquire. It fails safe (nothing runs twice), but it is not loud. Release is unaffected: `delete` raises on any `!`. On GitHub a real lost race reads `[rejected] (stale info | non-fast-forward | fetch first | already exists)` or `[remote rejected] (cannot lock ref …)`; I saw both shapes of the second in my run. A G1 option: treat only those reasons as `False` and raise `LockError` for any other `remote rejected`. That would be a spec change, which is the founder's call.
**What the spec says:** Deliver 1: "A ref line flagged `!` (rejected: `stale info`, `non-fast-forward`, `fetch first`, `already exists`) makes `create`/`update` return **False**."

### 4. Known answer 9 checks git's stderr through a proxy — **non-blocking (could be tighter, not wrong)**

**Where:** `v2/tests/tools/loop/test_lock_by_push.py:201`.
**What is wrong:** the test asserts that the missing remote's path appears in each `LockError`, not git's own wording. I checked that the code never puts the URL into a message itself (`_must` and `_push` add only the ref, the exit code and `err or out`), so the path can only come from git's stderr. The test does assert what the spec requires. A tighter version would also match git's text (`does not appear to be a git repository`).
**What the spec says:** known answer 9, "each raises `LockError` whose text includes git's stderr".

### 5. In a single-branch clone, `facts._locks` sees no lock tips at all — **non-blocking (pre-existing; for the gate)**

**Where:** `v2/tools/loop/facts.py` `_locks` and `_git`.
**What is wrong:** the report's "proves less than it looks" says this, and I confirmed it. `_git` returns `""` on failure, so a `lock/*` branch whose tip was never fetched reads as `(None, "")`, and `next_action._fresh(None)` treats it as not fresh. That was already true of *held* locks before this build. Deliver 4 works as specified wherever `lock/*` is fetched (the harness's fresh fetch shows it). In a cloud session's clone, the real guard is `Lock.acquire` at claim time, which asks GitHub directly. G1 may want `/chronos-tick`'s fetch to include `+refs/heads/lock/*:refs/remotes/origin/lock/*`.
