### 1. NON-BLOCKING — `_pages`' fail-closed guard is dead for every falsy non-list page, so a `null` or `{}` page silently truncates the halt feed instead of raising. Neither round found this; it is in this round's own new code.

*File and line:* `v2/tools/loop/facts.py:195-199`.

*What is wrong.* The guard is ordered so that the first line defeats the second:

```python
batch = api(f"{path}{joiner}per_page={_PER_PAGE}&page={page}", repo=repo) or []
if not isinstance(batch, list):
    raise FactsError(f"{path} page {page} is not a list of items")
if not batch:
    return out
```

`or []` runs first, so every **falsy** non-list — `None`, `{}`, `0`, `""` — becomes
`[]` before `isinstance` ever sees it, and `[]` is then read as the empty
terminator. The `isinstance` check therefore only fires for *truthy* non-lists. A
page that comes back unreadable in a falsy form does not raise: it ends the read,
and `_pages` returns the part it managed — which is precisely what the function's
own docstring says it must never do ("Fails **closed**. A feed that cannot be read
to its end raises rather than returning the part it managed, because a short read
of the halt feed reads as 'no emergency stop' — the one answer that must never be
guessed").

*Measured.* A feed whose page 3 carries the `labeled` event that starts a stop and
whose page 2 comes back unreadable:

```
page 2 = a GitHub error body {'message': ...}  -> FactsError (fails closed)  ok
page 2 = an empty object      {}               -> no raise; gathered 0; halt_in_force=False  *** STOP LOST ***
page 2 = a null body          None             -> no raise; gathered 0; halt_in_force=False  *** STOP LOST ***
page 2 = a zero               0                -> no raise; gathered 0; halt_in_force=False  *** STOP LOST ***
```

Only the truthy error body raises. The `_MAX_PAGES` bound is unaffected and still
raises on an endless feed, which I also checked.

*What the spec says.* Nothing directly — the spec does not specify a pagination
helper. The contract this breaks is the function's own, and the stop is the thing
it guards.

*Severity: non-blocking, and I considered blocking.* The reason it is not: the
failure needs a payload these endpoints do not produce. `_api` **raises**
`FactsError` on any non-zero `gh` exit, so every HTTP failure — the realistic
mode — takes the correct path; and I verified that all three endpoints the stop
reads return `[]` rather than `null` for an empty or past-the-end page, with `gh
api` exiting 0 and printing `[]`. So no Deliver item, Known-answers row or spec
rule is wrong for any input the system will see. It is also a hardening gap in a
defence this round **added** — round 1 had no pagination at all, so nothing
regressed. That puts it in the Severity block's "a test that could be tighter but
is not wrong" rather than "the code is wrong". It is still the finding I most want
fixed, because the path is the emergency stop and B04 and B05 build on it.

*Patch, verified.* Check the type before coercing, so an unreadable page of any
shape raises. As it is, `facts.py:195-197`:

```python
        batch = api(f"{path}{joiner}per_page={_PER_PAGE}&page={page}", repo=repo) or []
        if not isinstance(batch, list):
            raise FactsError(f"{path} page {page} is not a list of items")
```

as it should be:

```python
        batch = api(f"{path}{joiner}per_page={_PER_PAGE}&page={page}", repo=repo)
        if not isinstance(batch, list):
            raise FactsError(
                f"{path} page {page} is not a list of items; refusing to read it in "
                "part, because a short read of the halt feed would read as no stop"
            )
```

**Applied locally: 309 passed, ruff clean**, and all four payloads above then fail
closed. Reverted; the tree I reviewed is unmodified. *The test to add,* beside
`test_a_feed_too_long_to_read_is_an_error_not_a_short_read` which already
establishes the intent: parametrise a page that returns `None`, `{}` and `0` and
assert `FactsError` each time.

### 2. NON-BLOCKING — round 1's finding 3 is correctly declined, but the ground has shifted: round 1's stated reason for non-blocking is disproved, and there is a present-day hazard neither round named. This is the highest-priority item B04 inherits.

*File and line:* `v2/tools/loop/facts.py:237-244` (`gather` discovering refs with
`git ls-remote` against the **remote**) with `facts.py:272` (`_locks`),
`facts.py:287` and `:293` (`_build` reading `origin/<branch>` from the **local
clone**), and `facts.py:300` (`head_sha`).

*What is wrong, reproduced with real git rather than taken on trust.* I built a
bare origin, cloned it, and only then pushed a `claude/b06` branch carrying a
status file that says `changes_requested` with two review files on it, plus a fresh
lock — then never fetched. With G0 and G1 done and B01–B05 merged, so that B06 is
the entry actually under consideration:

```
BEFORE the clone fetches
  B06: branch=True state=None ticks=0 rounds=0 lock_at=None checks='pending'
  decide() -> RESUME_BUILD B06
AFTER the clone fetches
  B06: branch=True state='changes_requested' ticks=1 rounds=2 lock_at=fresh checks='green'
  decide() -> HALT B06
  spec row 17 requires: HALT B06 (failed review twice)
```

**Round 2's restatement is true and I confirm all of it**: the root cause reaches
four facts, not one, and a twice-failed build is resumed where row 17 says it must
halt. I also confirmed that there is no `git fetch` anywhere in `v2/tools/loop/` —
the only occurrence of the word is in a docstring.

*Why the ground has shifted.* Round 1 classified this non-blocking on two grounds:
that the spec never says `gather` fetches, **and** that it is defended in depth —
"`decide()` says resume, the agent calls `take_over`, the API says the real lock is
fresh, `take_over` returns `False`. A wasted tick and a misleading status report,
not two sessions building the same thing." Round 2's measurement **disproves the
second**: with the lock released and the branch unfetched there is no reference for
`take_over` to refuse, and nothing downstream catches it. A finding should not
inherit a classification whose reason has gone. I re-derived it instead.

*And a consequence neither round named.* This is not purely contingent on a B04
decision that has not been taken. B03 ships two entry points a human runs by hand
today — `next_action.py --ladder` and `status_report.py`, both with a `main` that
calls `gather` directly — and neither fetches. Run either from a stale clone this
week and it answers confidently and wrongly, with nothing on the screen to say so.

*What the spec says, including the strongest hook against the build.* Deliver 2
asks `facts.py` to gather "build branches and their status files, review-file
counts, lock references and their ages, check results on a branch head" — and does
not say against what repository state. The closest the spec comes to an affirmative
rule is "What the script trusts": "`round` is the number of review files on the
build's branch, **counted by the script**." The delivered script counts 0 for a
branch that has 2. I weighed that and do not think it converts the gap into a
violated rule: in context that sentence contrasts `round` (which the script
establishes, so a builder cannot misreport it) with `ticks` (which the builder
writes, so it can), and it is about provenance, not freshness. But it is the
strongest textual argument for blocking and a reader deserves to see it weighed
rather than skipped. Worth noting too that the same section reasons explicitly
about under-reporting being tolerable — "an under-reported number delays an
overrun halt and can do nothing else" — and that tolerance does **not** cover
this, because here an under-report turns `HALT` into `RESUME_BUILD`.

*Severity: non-blocking, on one ground rather than round 1's two.* The code is
correct for every repository state the spec describes and wrong only for a state
the spec never rules on — and which B03 cannot itself establish, because the thing
that maintains the loop's clone is B04, which has not chosen how. `gather(ladder,
repo_dir, …)` is correct conditional on `repo_dir` being current, and nothing
inside B03 can make that true. That is the Severity block's "a weakness in the
**spec** rather than the build". Round 2 also did the right thing procedurally:
it measured the finding rather than restating it, named the one-line fix on the
record so that declining is a decision rather than an omission, and refused to
change a dataclass and the decision layer over a non-blocking finding in a fix
round.

*The fix, for B04, which round 2 named and I endorse:* one line at the top of
`gather`, `git(repo_dir, "fetch", "--no-tags", "--prune", "origin")` — or the
clone-fresh-each-tick discipline, which closes all four symptoms without touching
`facts.py` at all. **B05 must not run anything unattended until one of them is in
place**, because B05 is the build that runs this with nobody watching and this is
the one defect in B03 that can make the loop take a wrong action.

## For the founder, in plain words

**The fix works, and it is better than it needed to be.** The emergency stop — the
`chronos-halt` label that is meant to freeze everything until you lift it — could
be switched off by the automation itself just by taking the label off the issue.

invisible; it treated *any* label coming off as the stop being lifted, so you

sends today, which is why it does not block the build.

**The one thing that must be fixed before the loop runs on its own.** The loop reads
some facts from its own local copy of the repository and does not refresh that copy
first. I reproduced this with real git: a build that has failed review twice and
must stop is instead told to carry on. It is a one-line fix, it belongs to the next
build because that build decides how the loop keeps its copy, and the previous
review's reason for thinking it harmless has turned out to be wrong. Nothing is at
risk today — nothing runs unattended yet — but **B05 is the build that turns this
