## The merge fix, attacked (hand-over item 1)

The disclosed hole is closed: break 2 confirms the restriction is load-bearing and tested. Going past it, I built seven throwaway repositories and asked the hand-over's question directly — *is there any path by which work enters a build branch and is judged by neither that branch's `scope` nor another pull request's?*

| Probe | Result |
|---|---|
| Octopus merge (base + side branch in one commit) | **charged** — `all()` over `parents[1:]` holds |
| Merge of base with `--strategy-option ours` (discards base's change) | **charged** |
| Merge of base with `--strategy-option theirs` | correctly **not** charged (base's own work) |
| Rename performed inside the merge commit | **charged**, both old and new path |
| File planted in the merge, present in neither parent | **charged** — the half that must not move, holds |
| `is-ancestor` unanswerable (shallow clone, missing commit) | **charged** — `_git_ok` returns false and the merge is charged in full, as documented |
| **Merge of an *intermediate* base commit** | **not charged by any guard** — finding 1 |

The shallow-clone case deserves a note: it fails safe in both directions. Truncated history can only make `--is-ancestor` *fail* to prove ancestry, never falsely prove it, so a shallow clone can over-charge but cannot exempt. The builder's "a guard that cannot tell must charge, not excuse" is implemented correctly.

**The builder's instruction to attack the principle rather than the command was the right instruction, and the principle is where the remaining gap is.** The stated principle — exempt only work "already judged somewhere else, the base branch's own pull requests" — has no clause for work that was judged on the base branch and then *withdrawn* there. Finding 1 is that clause missing.

**1. NON-BLOCKING — `paths_in` exempts a merge of an *intermediate* base commit, and nothing else examines what it brings in.**

*File and line:* `v2/tools/guards/gitrepo.py:203-212` (the exemption), with `gitrepo.py:105-112` (`diff_base`) as the second half of the mechanism.

*What is wrong.* The exemption fires when every parent after the first is an ancestor of `base_sha`. An **intermediate** commit on the base line satisfies that without the branch having caught up to `base_sha`, and merging one moves `diff_base` — the merge base — forward to it. Content that the base branch had at that commit and has since *withdrawn* then sits on the branch, charged to nothing:

- `scope` and `roles` iterate `ctx.commits` and judge `ctx.paths_in(sha)`; the combined diff (`--cc`) drops the file because it matches the second parent exactly, and `commits` has already skipped that parent's own commits with `--first-parent`;
- `protected` and `plumbing` iterate `ctx.changed_paths`, which is `diff_base..head` — and `diff_base` is now the merged commit, so the file is not a changed path either;
- `frozen_files` compares trees and would catch it, but only under `v2/tests/`, `v2/tools/v1_oracle/` and `v2/migrations/`.

So for a path that is neither founder-owned nor frozen — `v2/src/chronos2/**`, where the real code lives — there is no backstop. This is the same blind spot the builder disclosed and closed for side branches, reached by a different route.

*Measured.* A throwaway repository with base line A → B (adds `v2/src/chronos2/core/resurrected.py`) → C (deletes it), `base_sha` = C, branch cut from A as builder rule 1 directs, branch merges **B**:

```
scope=0  roles=0  protected=0  frozen_files=0
file present in head tree: yes       present on base: no
git diff --name-only v2-build...HEAD : does NOT list it
git diff --name-only v2-build..HEAD  : lists it
```

Zero findings, and the file is invisible in the three-dot diff that GitHub shows and that the guards compute.

*How far it reaches, stated honestly, because it is narrower than it first looks.* The content **cannot reach `v2-build`**: merging the branch back leaves the file deleted, because the three-way merge sees C's deletion against an unchanged head, and a squash merge applies `diff_base..head`, which does not contain it. I confirmed both. The payload is also limited to content that already exists in the base branch's history — a build cannot plant new code this way, only resurrect what the base once had and dropped. And it needs a deliberate `git merge <intermediate-base-sha>`; no ordinary workflow produces it.

What it does reach: the branch's own tree. `earlier_tests.FROM_HEAD_DIRS` copies `v2/src/chronos2` wholesale from the head, so a resurrected module is present and importable while the earlier builds' tests run, and a reviewer reading the three-dot diff never sees it. That is a real blind spot in a job built to be hard to fool.

*What the spec says.* Deliver 2's `scope` bullet: "every changed path is allowed for the role of the commit that changed it, with `touches` read from the spec **at the base commit**." The guard does exactly that for every path that is a changed path by its own definition; the scenario works by moving that definition. The spec's Known-answers table has no row for a merge of any kind — which is the builder's own O-20 — so there is no stated answer this contradicts.

*Severity.* Non-blocking. No Deliver item is missing or wrong, no Known-answers item lacks a test, no test was weakened, nothing outside `touches` changed. The Severity block names "a weakness in the **spec** rather than the build" as non-blocking, and that is what a missing row in the case table is. It also cannot put unjudged new code on the base branch. Recording it rather than halting on it is the rule working as intended: B02's code does what B02's spec asks, and the spec should ask for more.

*Patch, verified, offered although rule 7 does not require one for a non-blocking finding — it costs nothing and makes whichever build takes it mechanical.* `v2/tools/guards/gitrepo.py`, as it is:

```python
            from_the_base_alone = all(
                self._git_ok("merge-base", "--is-ancestor", parent, self.base_sha)
                for parent in parents[1:]
            )
```

as it should be:

```python
            from_the_base_alone = all(
                self._git_ok("merge-base", "--is-ancestor", parent, self.base_sha)
                for parent in parents[1:]
            ) and self._git_ok("merge-base", "--is-ancestor", self.base_sha, sha)
```

The added conjunct says the branch must actually have caught up: exempt a merge only when it leaves `base_sha` an ancestor of the merge commit. Both conditions are needed — the first alone admits finding 1, and the second alone re-admits the side-branch laundry the builder closed, since a branch cut from the base tip already has `base_sha` as an ancestor. **I applied it locally: 149 passed, all three existing merge tests included, and the probe above goes from zero findings to charged.** The case worth keeping as a test is the one above: branch cut from A, base at C, branch merges B, assert `scope` names the resurrected path.

**4. NON-BLOCKING — a stale `base_sha` charges a legitimate base merge in full.**

*File and line:* `v2/tools/guards/gitrepo.py:205-208`.

*What is wrong.* If the recorded `base.sha` is *behind* the base commit the branch merged, `--is-ancestor(merged, base_sha)` is false, the merge is charged in full against its first parent, and the branch is charged with everything the base did meanwhile — round 2's defect (A) in a new guise. Measured: a branch that merges the true base tip while `base.sha` is one commit older produces a `scope` finding **and** a `protected` finding naming `docs/v2/CHRONOS_V2.md`, a file no build may write. A clean build goes red for doing the right thing.

*Why it is not blocking.* It fails closed, so nothing gets through; GitHub refreshes `base.sha` on every `synchronize` event, so the ordinary round-2 merge is exempt (I checked the arithmetic against this branch's own history: merging `3c60c95` against `base.sha = 3c60c95` is exempt, and against a later `77bac0f` it is still exempt, because `3c60c95` is `77bac0f`'s first parent). Reaching the failure needs a workflow re-run on a stale payload, a base force-pushed backwards, or a race between the push and the event.

*For the gate.* This belongs with the builder's **O-20**: the guard cases have no row for the loop's second lap, and "the recorded base has moved" is a third missing row alongside "the branch merges its base" and "the builder returns after `changes_requested`".
