## Verdict: `CHANGES`

**Do not merge this yet. `/chronos-tick` does not work as shipped: the first
time you run it, it opens an emergency stop and freezes the loop.** The cause
is one line, the fix is four lines, and I have written the exact patch into
finding 11. Everything else in this build is sound.

**What goes wrong, measured rather than reasoned.** The helper runs
`next_action.py` as a subprocess with the working directory set to `v2/`, and
that script looks for the ladder at the *relative* path
`docs/v2/build/LADDER.yaml` — which, from `v2/`, does not exist. So the script
exits 1 with a `LadderError`, and `/chronos-tick` does exactly what Deliver 2
tells it to do when the script errors: it opens a `chronos-halt` issue with the
error text and stops. I drove the real `claim()` with a fake GitHub layer so
nothing was actually opened:

```
exit: 2
halt issues it WOULD have opened: 1
lock calls: []
next_action.py failed, so the loop opened chronos-halt issue #999 with the
error text and stopped. Nothing was claimed and nothing was committed.
  ...  ladder.LadderError: no ladder file at docs/v2/build/LADDER.yaml
```

**Three of the four commands are affected.** `/chronos-tick` halts the loop;
`/chronos-status` exits 2; the `finish` step's status report fails (it says so
rather than inventing one, which is correct behaviour on a broken call).
`/chronos-halt` and `/chronos-resume` are unaffected — they never touch these
two scripts. And because only you can close a `chronos-halt` issue, the first
tick would stop the loop until you cleared it by hand on GitHub.

**I applied my own patch and re-ran it before writing it down.** With it,
`claim()` returns exit 0 and `WAIT_FOUNDER B04` / "B04 needs you present; the
loop never runs it" / "Waiting on you: B04", and `/chronos-status` returns
"nothing is running. Next after that: B05. Waiting on you: B04." Those are
**the same outputs the report quotes as its smoke test** — which is how this got
through: the smoke test produced genuine output, but not through the invocation
the code actually ships. The full suite stays green under the patch (379 passed
plus the Postgres environment test, which fails only because Postgres had
stopped in my container), and `ruff` stays clean. I then reverted it: a reviewer
does not edit code.

**I got this wrong the first time and I am saying so plainly.** My first pass
reported `PASS` and I had already pushed that verdict and set the status to

## The four test assertions changed after they went red

This is the thing a reviewer should scrutinise hardest, and the builder said
so itself. Builder rule 2 and hard rule 8 both say a test is never weakened to
make something pass. I took each one separately, by diff, with the commit that
made it. **Three are stricter or spec-aligning; one is a real loosening, and I
accept it.** None lets failing code pass.

**(i) The two builder agents' front matter — `340f37e`.** Before: every
front-matter key but `name` and `model` had to match across the two builders,
which forced one shared `description`. After: the bodies must be
byte-identical (kept), each `model` is pinned (kept), the descriptions must
**differ** and each must name its own model, and everything else must still
match. Deliver 1 says "same **body**, different `model`" — it says nothing
about front matter, so the original assertion tested something the spec never
asked for. The replacement asserts more about the description than the
original did, not less. **Not a loosening.**

*But the stated reason is wrong, and it is worth knowing which part is wrong.*
The report and the test's own docstring say the shared description would have
made the two agents "indistinguishable" because "the description is what the
loop routes on". It is not: `loop_cli._agent_for` builds the agent name from
the action's model (`f"chronos-builder-{model}"`), and dispatch is explicit.
I grepped every module in `v2/tools/loop/` — the only occurrences of
"description" are two `argparse.ArgumentParser(description=…)` calls. The
change is still right (two agents with one description is a genuine problem
for any selection that is not explicit, and the spec never required them to
match); its justification names the wrong mechanism. See finding 3.

**(ii) `python -I` in the tick skill — `fe6ae4f`.** Before:
`assert "python -I" not in body`. After: the skill must contain `uv run python
tools/loop/next_action.py`, must contain the sentence "Never run it with
`python -I`", must mention `-I` at least once, and **every** line that
mentions it must contain "never". The original would have passed on a skill
that never warned about `-I` at all — including a future rewrite that
quietly dropped the warning. **Strictly stricter**, and the builder's claim
here is exactly right: the skill has to name the trap in order to prohibit it,
because `CLAUDE.md`'s own conventions tell sessions to use `-I`.

**(iii) The template section check — `fe8d857`. This one is a genuine
loosening, and the builder flagged it as such.** Before: `needle in text`.
After: `needle.lower() in text.lower()`. I accept it, on these grounds:

- The spec's Deliver 4 writes the section names as lower-case descriptive
  references — `review.md` (with "code commit reviewed")` — not as literal
  strings to match. The delivered template's heading is `**Code commit
  reviewed:**`.
- So the thing under test **does** satisfy the spec. The test was
  over-specified, asserting a capitalisation the spec never states; the
  correction aligns it to the spec rather than letting non-compliant code
  pass. That is the distinction builder rule 2 and the Severity block are
  drawing — "a test asserting **less than the spec states**" is blocking, and
  this now asserts exactly what the spec states.
- The weakened version still fails on a template that lacks the section, which
  is the requirement.

I record it as the closest call of the four, and I note for the gate that a
spec which wants an exact string should quote it as one (finding 9). A reader
who read "a test weakened between red and green" in the Severity block purely
mechanically, without the spec-relative reading the rest of that block uses,
could reach the opposite verdict. I do not, because the code was never
non-compliant.

**(iv) The lock test that passed down the wrong branch — `d5d06cb`. This is
the defect the builder found in its own work, and the fix is right.** The old
test built a lock whose commit message carried no `Chronos-Lock-At:` stamp, so
`lock.is_stale` raised, `claim` caught it, and the *unreadable-age* reply came
back — which also opens "claimed, nothing to do". The assertion passed without
ever reaching the branch the known answer is about. Verified against the code:
`loop_cli.py:283-292` has three distinct exits, and both `CLAIMED` and
`UNREADABLE_LOCK` begin with that sentence, so the original assertion could
not tell them apart.

The replacement is three tests, and I checked the thresholds rather than
trusting them — `lock.py:90` sets `claim_hours = 3`, so the fresh case
(5 minutes) and the stale case (4 hours) sit correctly either side:

- **fresh** — asserts `"Another session holds the lock"` is present **and**
  `"age cannot be read"` is absent, so it can no longer pass down the
  unreadable branch. It also builds the lock message with the real
  `lock.message_for` rather than by hand, which is what made the original
  wrong.
- **stale** — asserts the lock is taken over and the agent dispatched.
- **unreadable age** — asserts the lock is left alone.

**Neither new test is padding, and I can show it for the stale one.** My own
break (below) inverted one operator in `claim`'s staleness branch, and the
test that caught it was `test_tick_takes_over_a_stale_lock_and_dispatches` —
the stale case this correction added. Without it, as the builder argued, the
fresh case would pass equally well if `claim` always refused. The unreadable
case pins the behaviour the original test was accidentally exercising, which
is worth keeping on purpose.

### 10. `templates/review.md` and B02's `roles` guard disagree about what "code commit reviewed" means, and the template's reading fails the guard — **non-blocking** (a deliverable's guidance, and a rule that needs your decision)

**Where:** `docs/v2/build/templates/review.md:17-28`, against
