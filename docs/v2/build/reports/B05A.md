## What now exists that didn't before

The loop can now take and give back its lock from the cloud, which is where the scheduled task runs. Until today it could not: the lock was written through a GitHub route that the cloud session's network proxy refuses, so the loop could not run a single step on its own. The lock now works through `git push`, the same channel the cloud already uses to push branches. Proved against GitHub from a cloud session: 20 of 20 races to take a free lock and 20 of 20 races to take over an abandoned one each had exactly one winner, with no re-runs.

Giving the lock back used to fail silently: the old code threw away GitHub's answer, so "Lock released." could be printed over a lock still held. Now every outcome is read. A lost race is reported as "someone else has it", and any other failure (network, proxy, login) is reported as a fault with git's own words. A release that did not happen always says so. Because the cloud cannot delete a branch, a released lock now stays behind as a branch whose last commit says "released", and the loop reads it as free.

Nothing was left undone. **Design choices a reviewer should see stated:**

- **Any `!` line is a lost race (`False`).** The spec's parenthetical lists `stale info`, `non-fast-forward`, `fetch first` and `already exists`. On GitHub the loser of a real race came back `[remote rejected] (cannot lock ref …: reference already exists)` (the step 4 sample): both racers saw the ref absent, and GitHub's own compare-and-swap decided it. Reading the list as exhaustive would have raised `LockError` on a normal lost race (break 4 shows it). The consequence: a push refused by a server hook would also read as "someone else has it". That is the safe direction, since the session stops instead of running. Only a non-zero exit with no `!` line raises. `delete` raises on any failure, `!` included.
- **Pushes and fetches go to the remote's URL, not its name,** so git never updates a local remote-tracking ref as a side effect. Two racers in one clone would otherwise contend for that ref's lock file, a local failure that says nothing about who holds the lock.
- **`read` fetches the tip if it is not local.** If the tip moved between `ls-remote` and the fetch, it fetches the commit by sha. If that fails, `LockError`.
- **`main()` passes `--repo` to `production_refs` when given,** the same path `next_action.py` already receives; otherwise the repository root. `production_refs` accepts `github_repo` and does not use it: the clone's `origin` is the remote.
- **Known answer 10 races on a fresh absent ref per pair,** as "on an absent ref" reads; known answers 6 and 13 and the GitHub harness cover the released case.

## What this build proves less than it looks

- **The GitHub proof ran once, from one cloud session, on git 2.43.0, with this workspace's global `push.negotiate=true`.** The Mac's git, and a cloud session without that setting, are untested. The porcelain format has been stable for many git releases [Likely].
- **`facts._locks` skipping markers only matters in a clone that has fetched `lock/*`.** A cloud session's clone is single-branch (`+refs/heads/v2-build:refs/remotes/origin/v2-build`), and `/chronos-tick` runs `git fetch --no-tags --prune origin`, which then fetches no lock branch. There `_locks` sees each `lock/*` name from `ls-remote` but no tip, so it reports `(None, "")`, which `decide` treats as not fresh, the same as no lock. Nothing blocks, and that was already true of held locks before this build. In such a clone the loop's real lock check is `Lock.acquire` at claim time, which reads GitHub directly. Where `lock/*` is fetched (a full clone, the harness's explicit fetch), markers are skipped as specified.
- **The CI job `earlier-tests` does not exercise this build's code.** It takes from a pull request only `v2/src/chronos2/**`, migrations, `pyproject.toml`, `uv.lock` and the files in `may_modify_tests`, so it runs the base's loop code. `tools/loop/` changes are tested only by the branch's own full suite (`earlier_tests.py` docstring).
- **`loop_cli.py claim` was not run against GitHub.** Step 5 asks for `finish`; `claim` is covered by the frozen `test_agent_files.py` tests over `FakeRefs`, and its lock calls are the same `Lock` methods the harness drove against GitHub.
- **A hook-refused push reads as a lost race** (design choices, first item).

## For the gate

- **New traps for `BUILD_NOTES.md`:**
  - A lock released by a marker leaves its branch behind, so anything that reads `lock/*` must read the tip, not just test that the branch exists.
  - `git push --porcelain` and the exit code are the only trustworthy outcome of a push.
  - On GitHub, a lost push race can come back `[remote rejected] (cannot lock ref …)`, not `stale info`: treat every `!` as lost.
  - In a single-branch clone, `git fetch origin` fetches no `lock/*` tips.
  - `may_modify_tests` alone does not let a build edit a test: the `scope` guard admits only `touches`, so the file must be in both.
- **Spec defects (this spec):** Deliver 3 against the frozen `FakeGh` default; `may_modify_tests` without `touches`. Both fixed in #60.
