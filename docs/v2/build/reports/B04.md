## What now exists that didn't before

**The loop can now act, not just decide.** B03 built the part that works out
what should happen next; it had no hands. This build is the hands: four
commands you can type, and four job descriptions for the sessions that do the
work.

You now have **`/chronos-tick`**, which does exactly one thing and stops. It
brings the clone up to date, asks B03's script what is next, refuses if this
session is on the wrong model, takes the lock so two sessions can't collide,
hands the job to the right worker, releases the lock, and tells you where
things stand. **`/chronos-status`** answers "what is it doing?" in three
sentences. **`/chronos-halt`** stops everything. **`/chronos-resume`** turns
it back on — and refuses, every time, to lift an emergency stop, because an
automation that can switch off its own stop doesn't have one.

And there are now four written job descriptions in `.claude/agents/`: two
builders (one Opus, one Sonnet, same instructions), a reviewer and a gate
auditor. Each one pins the model it runs on, so the model a job runs on comes
from the job description rather than from whatever session happened to
dispatch it. Each one carries the rules for its role, the commit label it
must use, and the two things every session must do: read the spec from the
trusted branch, and check it still holds the lock before it pushes.

Three templates in `docs/v2/build/templates/` give the build report, the
review and the gate report a fixed shape, so each one is written the same way
every time and you learn to read it once.

**Four things needed your decision before any of it could be written, and
they changed what got built.** The spec asked for commands called `/tick`,
`/status`, `/halt` and `/resume` — but `/status` and `/resume` are already
Claude Code's own commands, and a command of ours cannot take a name one of
its own already uses. So all four carry a `chronos-` prefix. The details, and
the other three decisions, are under "Deviations".

## Deviations from the spec

**Four decisions were put to the founder before step 1 and all four were
answered together, which is why they are not halts.** They were raised at the
point they became clear, and all four answers landed before step 1's commit
at **17:28:04 UTC** — that bound is verifiable from the commit times; I did
not record a wall-clock minute for the answers themselves and am not going to
invent one.

1. **All four commands carry a `chronos-` prefix.** The spec's Deliver 2 and 3
   name `/tick`, `/status`, `/halt` and `/resume`. **`/status` and `/resume`
   are built-in Claude Code commands** — the official command reference lists
   both, `/status` as one that "works while Claude is responding" — and the
   official skills reference settles what would have happened: a skill's
   `name` sets the command you type *"unless another command already uses
   that name"*. So two of the four would never have been the founder's
   commands. Worse if one had won: `HANDBOOK` line 252 tells him to type
   `/status` to check which model he is on. The founder chose to prefix all
   four rather than only the two that clash, so there is one rule to remember
   and it stays safe if a later version adds a built-in `/tick` or `/halt`.
2. **A helper script, `.claude/skills/chronos-tick/loop_cli.py`, is an
   addition to Deliver 2,** which names only `SKILL.md`. Five of the spec's
   known answers are behavioural, and a `SKILL.md` is prose: there would have
   been nothing to assert and nothing for a reviewer to break. The mechanical
   parts live in the helper; dispatch stays in the `SKILL.md` because it
   cannot be code — a subagent is only reachable through the Task tool.
3. **The model check is done both ways,** and the spec's **second "Halt if"
   did fire.** A skill cannot read the session's live model:
   `ANTHROPIC_MODEL` is read at start-up and goes stale the moment anyone
   switches with `/model`, and no documented variable carries the live model
   into a shell command. The spec says that when this happens "the model check
   moves into the agent dispatch, and that is a design change to flag" — so
   this is the flag. The founder chose both halves: `/chronos-tick` compares
   the model the session is told it is running as, which keeps the handbook's
   promise but is a **guard rail** that depends on the session being honest
   about its own context; and every agent file pins its own `model`, which is
   the structural half. The handbook now says which is which instead of
   promising a check the design cannot enforce.
4. **The size budget: 16 files against a cap of 14.** Cleared, with markdown
   reported separately from the code cap. See "The actuals", including one
   correction to the figure he cleared on.

**Three further additions, none of them changing what the spec asks for:**

5. **`/chronos-tick` fetches before it gathers.** Deliver 2 says nothing about
   fetching. B03's round 2 declined its own finding 3 and handed this to B04
   explicitly as "one decision about the loop's clone discipline, and that
   decision is B04's". Without it, on a stale clone four facts read empty at
   once — a build's status, its review count, its lock age and its head sha —
   and a build that is in fact `changes_requested` twice over is told to
   `RESUME_BUILD` where row 17 says `HALT`. It is an addition because it makes
   the spec's own intent work rather than changing it.
6. **All four skills set `disable-model-invocation: true`.** Not in the spec.
   A command that takes a lock, dispatches a build or opens an emergency stop
   must never fire because a sentence happened to resemble its description.
7. **`CLAUDE.md`'s Build loop section keeps four bullets, not three.** A spec
   defect; see "For the gate".

**Design choices a reviewer should see stated rather than discover:**

- **No lock was taken for B04 itself.** `lock.py`'s backend writes git
  references through `gh api`, and every write route to `/git/refs` is refused
  in this session: `POST` and `DELETE` both return `403 "Write access to this
  GitHub API path is not permitted through this proxy"`, measured. `git push`
  and pull-request creation do work. So this session could not take a lock
  and, had it managed to, could not have released one. B04 is `who: founder`
  and the loop never starts it, so nothing could collide. This session is
  **more restricted than B03's**, which could at least create references.
- **The reviewer agent's tool list is not the boundary it looks like.** The
  spec asks for "no file-editing tools beyond what writing the review and
  status files needs". A `tools:` list cannot express "only these paths", so
  the file says so plainly and names what does enforce it: the `roles` guard,
  which refuses a reviewer commit that touches code. `disallowedTools: Task`
  does stop it delegating the edit to someone else.
- **The auditor carries no role trailer,** and its body says why: `roles`
  returns early when there is no build id, so it does not bind a `gate/gN`
  branch, and borrowing either role's label would be exactly the false
  labelling the gate audit exists to catch.
- **The `CLAUDE.md` bullet check pins a digest rather than reading git.**
  `.github/workflows/v2.yml` uses `actions/checkout@v4` with no
  `fetch-depth`, so the tests job gets one commit and no `v2-build` ref: a
  test that shelled out to `git show origin/v2-build:CLAUDE.md` would be green
  here and red on the runner, which is B03's git-identity defect exactly. The
  bytes are pinned as a sha256 instead — B03's own precedent of frozen copies
  — **and** the live comparison the spec asks for was run by hand, with the
  extraction `diff`ing identical and hashing
  `a95ff6461b7b155d7bdf616f975c750616496e4772ce84d20eaf2458a32309fe`.
- **Three of my own test assertions were corrected after step 1**, each
  disclosed in the commit that changed it, because changing a test after
  seeing it fail is the thing a reviewer should scrutinise hardest. None was
  loosened to make failing code pass; two are strictly stricter. (i) I had
  required every front-matter key but `name` and `model` to match across the
  two builders, which would have forced one shared `description` — and the
  description is what the loop routes on, so the two would have been
  indistinguishable; the spec says "same **body**". It now asserts the bodies
  are byte-identical and each description names its own model. (ii) I had
  asserted `"python -I"` never appears in the tick skill, but the skill must
  *name* `-I` to warn against it; it now asserts every mention sits in a
  prohibition. (iii) The template section check is case-insensitive: the spec
  writes those names as lower-case descriptive references while a heading
  capitalises naturally.
- **`v2/tests/tools/loop/conftest.py` was not touched.** It already puts
  `v2/tools/loop` on `sys.path`, which this build's test needs; it exists on
  the base branch and is frozen.

## What this build proves less than it looks

**The model check is a guard rail and nothing more.** It works by the session
comparing the model it is told it is running as against the one the action
asks for. A session that misreports its own model defeats it, and no test can
catch that. The structural half — each agent pinning its own `model` — is
what actually holds, and it holds only for dispatched work, not for a founder
typing `/chronos-tick` on the wrong model and ignoring the warning.

**Every agent body is unexercised prose.** The four definitions were loaded
live by this session as they were written, which proves the front matter
parses and the tool lists apply — the builders came back "All tools" (no
`tools` key, so inherited), `chronos-reviewer` as "Read, Write, Edit, Bash,
Grep, Glob" with `Task` absent, `chronos-auditor` the same plus `WebSearch`
and `WebFetch`. That is the front matter proved. **Nothing here proves an
agent follows its body.** The tests assert the instructions are present, not
that they are obeyed. B05 is the first time one of these runs unattended.

**The toy cycle's reviewer and builder were this session, wearing two hats.**
The whole point of the design is that they are different sessions, and the
toy run cannot demonstrate that — it demonstrates that the *artefacts* a
three-tick cycle produces satisfy the role checks. Builder–reviewer
separation remains what the blueprint calls it: a guard rail, kept by the
loop starting a fresh session per action, checked afterwards at each gate.

**`GitHubIssues.open_halt_issue` has never run.** Opening a real
`chronos-halt` issue would freeze the loop, so I did not. Its read half ran
against the live API and correctly returned `None`; its write half is covered
only by the fake layer. The `chronos-halt` label still does not exist in this
repository — B03 said whoever turns the loop on should create it first, and
that is still true, and the first real stop is still worth watching by hand.

**The helper is not linted by CI.** `uv run ruff check .` runs from `v2/`, and
`loop_cli.py` is at `.claude/skills/chronos-tick/`. I linted it by hand and it
is clean, but nothing on GitHub will notice if that stops being true. Listed
for the gate.

**One tick, and the lock never contended.** The toy run took and released the
lock three times with no competitor. B03 proved contention against real
GitHub — 40 races, one winner each. Nothing here adds to that.
