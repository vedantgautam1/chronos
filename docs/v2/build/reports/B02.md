## What now exists that didn't before

**Every pull request in this repository is now checked automatically, by code the pull request cannot change.** Before today a build session could have edited the test that judged it, widened the list of files it was allowed to touch, quietly loosened an earlier build's assertion, or marked its own work as reviewed, and nothing would have noticed. Seven checks now look for exactly those things on every pull request, and they read their own code — and the build's own rules — from the branch being merged *into*, not from the branch being judged. A branch that rewrites the checker changes nothing, and there is a test that proves it: a branch which replaces the checker with "pass everything" **and** edits frozen v1 code still fails.

A second check re-runs the earlier builds' tests, taken from the approved copy, against this pull request's code. Four specific ways of switching an earlier test off without deleting it — the two a red-team session actually used to beat an earlier design — now each end with the job red.

Alongside the checks, two things the founder owns now exist on paper: `.github/CODEOWNERS`, which says every file in the repository is his except the folders builds work in; and `v2/config/protected/validation.yaml`, which holds the six validation numbers already locked in the master document, each labelled with the decision it came from. Any pull request that changes that file prints the old and new values in its summary, so the founder sees the diff he is approving.

**What this is not.** These are **tripwires**, not walls. Every one of them can be got around by a session that sets out to deceive, and the code says so in its own docstrings, in the summary it prints, and in a table in the spec that lists each gap and what catches it. Two things in particular stay on trust until later builds: the role label on a commit is something a session writes about itself, and both roles use the same GitHub account; and new code inside the package can still defeat a test from the inside. The walls come at B05, when GitHub's own rules are switched on and then attacked, and at each gate's audit.

## One place this build proves less than it looks

The fourth of the four tricks — a pytest plugin arriving through `uv.lock` alone — is tested more weakly than the other three, and its test says so in its own docstring. It asserts that the lock file **is** one of the four paths taken from the branch, that the trick is therefore present in the tree, that the job runs with entry-point plugin loading switched off, and that the earlier failing test still fails. It does **not** install a real distribution into a temporary environment and watch it fail to load; that is outside this build's size. Read it as a test of the control (`PYTEST_DISABLE_PLUGIN_AUTOLOAD`), not as proof that no real plugin can load. `plumbing` separately fails any lock change in a build whose spec names no new library, and the lock file is founder-owned.

## The test that closes the class, not the instance

`test_every_piped_run_step_sets_pipefail` parses the workflow and, for every step whose `run` contains a real pipeline, asserts the step sets `shell: bash` **or** contains `set -o pipefail`. Either fix is sufficient and it accepts either.

One judgement worth the reviewer's eye: `||` is stripped before looking for `|`. ## Two new defects — found this round, fixed this round on the founder's instruction

Neither is in the review. Both are in guard code inside this build's `touches`, and both were invisible until now because this is the first round 2 and the first time a branch has merged the base under the guards. They were put to the founder with the option of leaving them for the reviewer to log; **he chose to fix them in this round.**

**(A) A merge commit was charged with the merged-in branch's work.** `gitrepo.paths_in` diffed a commit against its *first* parent, so for a merge everything the second parent brought in read as the merge commit's own work. Measured on this branch: merging `v2-build` in charged `073c548d` with `docs/v2/CHRONOS_V2.md`, `docs/v2/build/LEDGER.md` and `docs/v2/build/specs/README.md` — three paths no build may ever write. `commits` already makes this judgement one level up with `--first-parent`, and says so: "a commit that arrived because the branch merged another branch in belongs to that branch." The exclusion stopped at the merge commit itself, which sits on the first-parent line.

*Fixed* by judging a merge on its combined diff (`diff-tree --cc`): the files whose merged content differs from **every** parent. A file taken verbatim from one side drops out. What stays charged is what the merge itself decided — a hand-resolved file, a file git auto-merged from both sides, and a file planted in the merge that exists in neither parent. `test_a_change_smuggled_into_a_merge_is_still_caught` is the half that must not move.

**(B) A builder commit was charged with a status an earlier commit set.** `roles` read the status file as it *stood* at each commit rather than asking whether that commit *wrote* it. So once a reviewer sets `changes_requested`, every builder commit of the next round is found to have "set the status to `changes_requested`" without touching the file. Measured: `28b4f321` and `305b419c`, neither of which goes near `status/B02.json`; the last commit that actually set it is the reviewer's `caf7b32`. **This would have fired on every round 2 there will ever be** — a build that needs a second round could never show a green gate.

*Fixed* with `_status_set_by`, which returns the state a commit set and `None` when the commit did not write the file. `_status_state` keeps its old meaning and is still what `_review_backs_the_status` asks of the head commit, where "the state as it stands" is the right question. The half that must not move: a builder writing a reviewer's state still fails, asserted in the same test.

**Why these are worth a note at the gate.** Both are the same shape of mistake — attributing to a commit something it did not do — and both were invisible to a 109-test suite, a careful review and a green CI run, because nothing had exercised a second round or a base merge. The guards were written from the spec's table of cases, and the table has no row for "the branch merges the base in" or "the builder comes back after `changes_requested`". The cheapest general fix is a case for each in whichever build next touches this folder.
