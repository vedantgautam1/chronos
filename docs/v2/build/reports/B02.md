## What now exists that didn't before

**Every pull request in this repository is now checked automatically, by code the pull request cannot change.** Before today a build session could have edited the test that judged it, widened the list of files it was allowed to touch, quietly loosened an earlier build's assertion, or marked its own work as reviewed, and nothing would have noticed. Seven checks now look for exactly those things on every pull request, and they read their own code — and the build's own rules — from the branch being merged *into*, not from the branch being judged. A branch that rewrites the checker changes nothing, and there is a test that proves it: a branch which replaces the checker with "pass everything" **and** edits frozen v1 code still fails.

A second check re-runs the earlier builds' tests, taken from the approved copy, against this pull request's code. Four specific ways of switching an earlier test off without deleting it — the two a red-team session actually used to beat an earlier design — now each end with the job red.

Alongside the checks, two things the founder owns now exist on paper: `.github/CODEOWNERS`, which says every file in the repository is his except the folders builds work in; and `v2/config/protected/validation.yaml`, which holds the six validation numbers already locked in the master document, each labelled with the decision it came from. Any pull request that changes that file prints the old and new values in its summary, so the founder sees the diff he is approving.

**What this is not.** These are **tripwires**, not walls. Every one of them can be got around by a session that sets out to deceive, and the code says so in its own docstrings, in the summary it prints, and in a table in the spec that lists each gap and what catches it. Two things in particular stay on trust until later builds: the role label on a commit is something a session writes about itself, and both roles use the same GitHub account; and new code inside the package can still defeat a test from the inside. The walls come at B05, when GitHub's own rules are switched on and then attacked, and at each gate's audit.

## Deviations from the spec

There should be none. There is one, and the founder was asked about it before this build was handed over; he chose to record it here rather than halt for a spec correction.

**1. The `earlier-tests` tree is the whole base checkout, not the base's `v2/` folder.**

The spec says the job "starts from a clean checkout of **the base commit's `v2/` folder**". Built literally that way, the job is red on every pull request from now on for a reason that has nothing to do with the pull request: B01's `v2/tests/test_workflow_file.py` reads `.github/workflows/v2.yml`, which is outside `v2/`, so three earlier tests cannot find their file. The tree is therefore the whole base checkout, with the same four things taken from the branch and nothing else (`v2/src/chronos2/**`, `v2/migrations/**`, `v2/pyproject.toml`, `v2/uv.lock`, plus any file the base spec lists in `may_modify_tests`).

Why this is the right reading rather than a loosening: the spec's own standard for the comparison is "the set collected on **an untouched base checkout**", and the job's purpose is the earlier tests "run as they were approved", which requires whatever those tests open. It is also strictly the safer direction — everything outside the four taken paths is still the base's copy, so nothing the pull request put anywhere else is present. `BUILD_NOTES.md` §1 now carries the general trap.

**Not a deviation, but flagged for the reviewer** (three things a reviewer should expect to see and would otherwise have to judge cold):

- **`v2/tests/tools/guards/conftest.py` adds `v2/tools/guards` to `sys.path`.** This is the one import-affecting line in the build. The guards live outside the `chronos2` package and B02's spec does not list `v2/pyproject.toml` in `touches`, so `pythonpath` could not be set there. The file defines fixtures only — no `pytest_*` hook, no `autouse` — which is what the `plumbing` guard it is testing requires of it.
- **The decision to extract the base's guard code lives in `v2/tools/guards/run_guards.sh`, not in the workflow YAML.** It is the one property the whole design rests on, so it is in a script the tests drive directly; shell inside the YAML would be untested. Both jobs go through that one script, so there is a single extraction path and a single entry point. A test asserts the workflow calls it.
- **Three step-1 test files were edited after step 1.** All three are disclosed in the commit that made them, because "a test weakened between red and green" is a blocking finding. None weakened anything: two were repo-setup bugs in the temp-repository factory (`git branch` on a branch that already existed, and `git branch -f` on the branch currently checked out, which made four cases die in setup rather than run), and one changed `owners == [founder]` to `list(owners) == [founder]` because the field is a tuple. No assertion, tolerance, expected value or seed was touched.

## One place this build proves less than it looks

The fourth of the four tricks — a pytest plugin arriving through `uv.lock` alone — is tested more weakly than the other three, and its test says so in its own docstring. It asserts that the lock file **is** one of the four paths taken from the branch, that the trick is therefore present in the tree, that the job runs with entry-point plugin loading switched off, and that the earlier failing test still fails. It does **not** install a real distribution into a temporary environment and watch it fail to load; that is outside this build's size. Read it as a test of the control (`PYTEST_DISABLE_PLUGIN_AUTOLOAD`), not as proof that no real plugin can load. `plumbing` separately fails any lock change in a build whose spec names no new library, and the lock file is founder-owned.

## For the gate

**Status board (§2).** "Build blueprint + build loop" — the guards are built. Phase 0 is two of five builds done (B01, B01A merged; B02 awaiting review).

**New traps, added to `BUILD_NOTES.md` §1** (this build's spec lists that file):
- the guards run on `pull_request` with code and specs read from the base commit; they are tripwires; the base-context variant of the event is not used, and why, with both GitHub facts re-confirmed at build time;
- on `pull_request`, check out the head commit explicitly — the default is the synthetic merge commit, which carries no role trailer;
- a job that rebuilds a tree from one folder breaks any test that reads outside it (the deviation above, generalised);
- a text scan written as a bare pattern matches its own source — B02's `autouse` note did exactly that and printed an untrue line before it was narrowed;
- CODEOWNERS' three easy-to-reverse semantics, and why the file is written as "everything is the founder's, except…".

**Adopted libraries: none.** The guards are standard library only — deliberately, so they still run when a pull request has broken the environment. `protected_values.py` uses `pyyaml`, which B01 already has, and is not imported by the guard runner.

**Open questions this build raises, for the founder:**

- **O-17 (new): the guards do not check themselves.** `earlier-tests` takes only the package, the migrations and the dependency files from a pull request, so a later build that changed `v2/tools/guards/` would have the **base's** guard tests run against the **base's** guard code — proving nothing about its change. In practice `v2/tools/guards/` is founder-owned and `protected` refuses it unless a spec lists it, so this matters only for the handful of builds whose specs do (B03, B04, B05). Worth a decision at G1: either those builds' pull requests get the full suite from their own branch as the check (which the ordinary `v2` workflow already does), or the guard folder joins the four paths `earlier-tests` takes.
- **O-18 (new): non-build `claude/…` branches now fail `branch_kind`.** The repository has several (`claude/review-severity-rule`, `claude/lock-v2d51`, `claude/build-blueprint`), all merged before today. From now a branch named `claude/<anything that is not a build id>` into `v2-build` is refused, with the finding naming `doc/…`, `spec/…`, `lane/…` and `gate/gN` as the alternatives. This is what the spec asks for; it is recorded because it changes a habit.
- **The size budget was overrun and the founder cleared it mid-build** — see the actuals below. This is the first build where 2.7's numbers have been measured against reality, and they were wrong by a wide margin.

**Not in this build, by design.** The proofs on GitHub are the first step of **B03**: they need this build's guard code to be on the base branch already, so run here they would go red for the wrong reason and prove nothing (red-team third pass, finding h). GitHub rulesets and the automation's own identity are B05. Mutation testing is B22.

**On the overrun.** The code is 3.5× the cap on the stricter count and 4.8× on the raw one; the tests are 1.7× and 2.5×. Builder rule 9 makes a size overrun a halt only the founder clears, so it was put to him at the point it became clear — 543 lines in with roughly 600 more needed — with three options: carry on and record it, halt and split B02, or drop the `earlier-tests` job into its own build. **He chose to carry on and record it.** The argument for that was that 2.7's caps are explicitly "[Guessing — to be measured]" proxies for *session-fit*, and session-fit held comfortably: one tick of three, one unhurried session, no sign of running out. The argument against, which the reviewer and the gate should weigh: the red team had already split phase 0 once on exactly this basis (finding 17), B02's deliverables do interlock but not inseparably, and a build 3.5× over its cap is not a rounding error.

**What G1 should take from this.** One data point, not a trend — but if a measured M build needs ~1,400 lines of code and ~1,000 lines of tests, then either M's caps are far too low for infrastructure builds, or infrastructure builds need a size class of their own separate from the statistics and data builds the caps were sketched for. The ledger row is the evidence; B03 and B04 will say which.
