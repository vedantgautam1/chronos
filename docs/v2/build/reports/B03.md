## What now exists that didn't before

**The loop can now work out for itself what to do next, and an ordinary script does it — not an AI.** Before this build, deciding "which build is next, is anything half-finished, is anyone else already working on it, is the emergency stop on?" was a judgement call a session made by reading documents. Now it is a program: it reads the ladder, looks at the branches, the status files and GitHub, and prints one answer with a one-line reason in plain English. The AI sessions only do the job it names. That means "what is the loop doing?" has a single checkable answer rather than an opinion, and a session cannot talk itself into starting work that isn't next.

It also now takes a **lock** before acting, so two sessions can never build the same thing at once; and it can say where things stand in three sentences you can read in ten seconds — *"B09 is waiting to be reviewed, round 1. Next after that: B10. Nothing is waiting on you."*

**And before any of that, this build did the job it was really there for: it put B02's guards on trial for the first time.** Every check B02 ran on itself was marking its own homework — the code doing the checking *was* the code being checked. Step 0 ran five deliberate breakages past those guards from a different branch, and all five were caught, for the right reasons, with the guard code coming from the trusted copy rather than the branch's own. **One of those five is the first time the second safety net has ever been seen to catch anything on GitHub at all.**

One thing could not be done from the building session and was finished afterwards: the lock's proof against GitHub itself, which needed to write git references the session was blocked from writing. The founder ran it on his Mac and **it passed** — 40 races, one winner every time. One thing is recorded rather than smoothed over: the build is over its size budget, which the founder cleared mid-build.

## Step 4(ii) — the lock, proved against GitHub

**Run on the founder's Mac at 22:19 UTC on 19 Nov 2026, after the building session could not run it.** Result: **PASSED**, both races, 20 of 20 pairs with exactly one winner each, every reference deleted and verified gone.

```
--- race 1 of 2: 20 racing acquire pairs ---
    20 of 20 pairs had exactly one winner.

--- race 2 of 2: 20 racing take_over pairs ---
    20 of 20 pairs had exactly one winner.

RESULT: PASSED
  acquire   20/20 pairs, exactly one winner each
  take_over 20/20 pairs, exactly one winner each
  every lock/zz-proof-* reference deleted and verified gone
```

The harness is `v2/tools/loop/prove_lock_on_github.py`. It drives the **real** `GitHubRefs` and `Lock` rather than a reimplementation, so what was proved is the code the loop actually runs. Before the races it ran a preflight — create, fast-forward, delete one reference — so a machine that could not write references would have failed in seconds rather than halfway through.

### What the run established that the documentation does not

The spec tagged both of the lock's load-bearing claims `[Likely — standard API behaviour; proved in step 4]`. GitHub's documentation, read fresh the same day, confirms that `force` defaults to `false` and means "make sure the update is a fast-forward update" — but **states the status code for neither refusal**. The run supplied both. They are recorded here and in `lock.py` because nothing else documents them:

| Claim | Observed | **Now** |
|---|---|---|
| creating a reference that already exists is refused | `422 "Reference already exists"` | **[Certain — run]** |
| a non-fast-forward update with `force: false` is refused | `422 "Reference cannot be updated"` | **[Certain — run]** |

### Sample API exchange — racing `acquire`, pair 00

Two sessions, two commits, one reference. The loser is refused:

```
POST git/refs  {"ref": "refs/heads/lock/zz-proof-acquire-00", "sha": "8cce7ba1..."}
  exit 1  {"message":"Reference already exists", ... "status":"422"}

POST git/refs  {"ref": "refs/heads/lock/zz-proof-acquire-00", "sha": "15f11087..."}
  exit 0  {"ref":"refs/heads/lock/zz-proof-acquire-00", "object":{"sha":"15f11087..."}}
```

### Sample API exchange — racing `take_over`, pair 00

Both sessions read the same stale commit `83d6f142…` and both built a commit on it. The first update is a fast-forward and is accepted; the second is no longer a descendant and is refused:

```
POST git/commits  parents ["83d6f142..."]  session-a -> 8cd96858...
POST git/commits  parents ["83d6f142..."]  session-b -> 512df0fa...

PATCH git/refs/heads/lock/zz-proof-takeover-00  {"sha": "512df0fa...", "force": false}
  exit 0  {"ref":"...","object":{"sha":"512df0fa..."}}

PATCH git/refs/heads/lock/zz-proof-takeover-00  {"sha": "8cd96858...", "force": false}
  exit 1  {"message":"Reference cannot be updated", ... "status":"422"}
```

**This is also the content-addressing trap, caught in the act.** The two commits have the same tree and the same parent and differ only in their `Chronos-Lock-Session` line — `session-a` against `session-b` — and that alone is what makes them two objects (`8cd96858` and `512df0fa`) rather than one. Had the messages been identical, GitHub would have been handed the same sha twice, both updates would have trivially succeeded, and **both racers would have believed they held the lock**. The break test in `test_lock.py` that removes the session id is not a formality; this run shows exactly the mechanism it protects.

### The halt this clears

The build was `halted` on this step and nothing else. The spec's second Halt-if — *"two winners in either race, or GitHub accepts a non-fast-forward update with `force: false`"* — did **not** fire, so the lock design stands and no alternative needs proposing. Status moves to `needs_review`.

**What this does not prove**, stated because the distinction is the whole reason the proof exists: it shows GitHub refuses those two things *today, on this repository, for this account*. It is a tripwire that has now been seen working, not a guarantee about future API behaviour. B05's attack tests are what re-check this class of assumption once the automation has an identity of its own.

**One of those twelve is a finding, not a formality.** Dropping the session id from the lock commit message produces **two winners** in the take-over race. Git commits are content-addressed: two sessions racing to take over the same stale lock build their commits on the same parent, with the same (empty) tree, so if their messages are identical the two commits are *the same object*, both updates trivially succeed, and both sessions believe they hold the lock. The session id in the message is the only thing making them distinct. This is written down because it is invisible from the code and a later build tidying that message would reintroduce it.

### One defect CI caught that every local run hid

Worth its own heading because it is the cleanest example in this build of CLAUDE.md rule 8 — *"tests green" is not "it works"*.

The lock races shell out to `git commit-tree`, which needs an author identity. This machine has a **global** git identity, so the 40 races passed locally every time I ran them. The CI runner has none, so run `44618675560`'s tests job failed: **10 failed, 261 passed**, every failure `LockError: Author identity unknown`. The test was quietly depending on ambient machine configuration.

Fixed by giving the throwaway bare repository an identity of its own, in the environment of every git call it makes as well as in its own config, so the test depends on nothing outside the repository it creates. **Verified against the real condition rather than assumed:** the whole suite re-run with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null`, which reproduces a runner with no git identity at all — 271 passed. Both workflows are now green on the head commit: `v2-guards` (`44619544943`) both jobs, and `v2` (`44619544917`) all three.

### A fourth defect, found after the report was first written

Found while explaining step 4(ii) to the founder, by printing the paths `GitHubRefs` actually builds rather than reading the code again.

**`GitHubRefs.delete` asked for `repos/<repo>/git/heads/<name>`.** The endpoint is `/repos/{owner}/{repo}/git/refs/{ref}`, so the path was missing the `refs/` segment and would have 404'd every time. **`release()` could therefore never have released a lock** — every action would have left its lock behind to time out over `claim_hours`, so the loop would have serialised itself to roughly one action every three hours while appearing to work. `read()` and `update()` were correct, but all three built their paths by separate inline string replacements, which is how one of them came to be wrong; they now share one `_path()` helper.

**Seven tests now assert the exact routes and bodies the backend builds**, with a fake runner and no network. They exist precisely *because* step 4(ii) could not be run from the building session: the one thing that can be checked without GitHub is that the backend asks for the right routes, and that check found this immediately. Reintroducing the old path makes three of them fail. This is the clearest argument in the build for not letting an unrunnable proof stand as an excuse for an unchecked code path — and the point is sharpened by what happened next, because step 4(ii) then ran and passed **through this same `delete`**, which would have failed every clean-up call had the route not been fixed first.

3. **The size budget is overrun** — cleared at **about 20:22 UTC, 19 Nov**, when it became clear, not at the end. See "The actuals". Three further design choices that are not deviations but that a reviewer should see stated rather than discover:

- **`load()` takes a `spec_root`, and the frozen fixtures are loaded without one.** The spec's validation list includes "a spec path exists unless it is `card`". `ladder_b.yaml` has to give B23 and B24 spec paths to make them startable, and those two spec files do not exist — so loading the fixture with path-checking on would fail for a reason that has nothing to do with the decision table. The rule is therefore enforced where it means something (`test_the_live_ladder_validates`, which loads the real `LADDER.yaml` with `spec_root` set) and has its own negative test (`test_rejects_a_spec_path_that_does_not_exist`). The fixtures say this in a comment at the top.
- **A `conftest.py` in `v2/tests/tools/loop/` adds `v2/tools/loop` to `sys.path`.** The loop code sits outside the `chronos2` package and B03's spec does not list `v2/pyproject.toml`, so `pythonpath` cannot be set there. This is exactly the precedent B02 set and disclosed for `v2/tests/tools/guards/conftest.py`. The file holds no `pytest_*` hook, no autouse fixture and nothing that changes which tests run — the `plumbing` guard forbids that, and this file is inside the folder it polices.
- **Rows 30, 30b, 30c, 31, 37, 37b and 39 are asserted at the facts layer as well as the decision layer**, because that is where they are implemented. `decide()` sees one boolean for the emergency stop; `halt_in_force` is what computes it from each issue's timeline. Asserting those rows only against `decide()` would have made three of them the same test.

**No known answer in the spec was changed.** Nothing outside `touches` (`v2/tools/loop/**`, `v2/tests/tools/loop/**`) was modified, apart from the builder's own three allowed paths: this report, the CHANGELOG section and `status/B03.json`. ## One thing this build proves less than it looks

**`facts.gather` is the least-tested thing here, and it is the part that touches the real world.** Its pure pieces are well covered — `halt_in_force`, `validate_status`, `_pull_requests`, `_checks` all have their own tests, including negative ones. The assembly around them has been exercised end to end exactly once, by the step 6 dry run, against a toy repository with GitHub stubbed. That single run is what found the `checks` bug, which is evidence both that the dry run is valuable and that one run is thin cover.

Concretely, these have never been exercised against the real repository: `_locks` parsing a real lock commit (no lock reference has ever existed), `_pr_state`'s review half against a real pull request, and `_halt_issues` against a real labelled issue. The decision logic for all three is tested; the wiring that fills them has only ever run against stubs. B04 drives this code for the first time in anger and B05 runs it unattended, which is where those gaps will show.

**One of these was worse than untested, and is now fixed rather than merely disclosed.** While writing this section I found that `_pr_state` read its review state from `_reviews` and `_needs_owner_review` keys that **nothing populated**, so the code-owner review state was always `None` — which would have made rows 28, 28b and 28c correct in `decide()` and unreachable through `gather()`. Deliver 2 asks in so many words for "pull requests for build and gate branches (open, merged, closed unmerged, **waiting on code-owner review**)", so this was a Deliver item half-built, not a gap in the spec. `_pull_requests` now fetches each open pull request's reviews and `_pr_state` reads them: the founder is the sole code owner, so "waiting on him" means he is a requested reviewer and has not yet approved, and only his latest verdict counts. Ten tests cover it, and three breaks confirm they bite — a `COMMENTED` review counting as a verdict, anyone's approval counting as his, and reviews being fetched for closed pull requests all go red.

That leaves the honest position: the review half of `_pr_state` is now implemented and unit-tested against stubs, and still unexercised against a real pull request.
