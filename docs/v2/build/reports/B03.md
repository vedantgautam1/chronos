## What now exists that didn't before

**The loop can now work out for itself what to do next, and an ordinary script does it — not an AI.** Before this build, deciding "which build is next, is anything half-finished, is anyone else already working on it, is the emergency stop on?" was a judgement call a session made by reading documents. Now it is a program: it reads the ladder, looks at the branches, the status files and GitHub, and prints one answer with a one-line reason in plain English. The AI sessions only do the job it names. That means "what is the loop doing?" has a single checkable answer rather than an opinion, and a session cannot talk itself into starting work that isn't next.

It also now takes a **lock** before acting, so two sessions can never build the same thing at once; and it can say where things stand in three sentences you can read in ten seconds — *"B09 is waiting to be reviewed, round 1. Next after that: B10. Nothing is waiting on you."*

**And before any of that, this build did the job it was really there for: it put B02's guards on trial for the first time.** Every check B02 ran on itself was marking its own homework — the code doing the checking *was* the code being checked. Step 0 ran five deliberate breakages past those guards from a different branch, and all five were caught, for the right reasons, with the guard code coming from the trusted copy rather than the branch's own. **One of those five is the first time the second safety net has ever been seen to catch anything on GitHub at all.**

Two things are **not** finished, both recorded below rather than smoothed over: the lock's proof against GitHub itself could not be run from this session, which is why the status is `halted`; and the build is over its size budget, which the founder cleared mid-build.

## The halt — step 4(ii), and nothing else

**Every other step is complete and green.** The status is `halted` for one reason: the lock's proof against GitHub itself could not be run from this session.

Step 4 asks for two proofs. The first — 20 racing `acquire` pairs and 20 racing `take_over` pairs against a throwaway local bare repository — is done and passing. The second — the same 40 races **against GitHub**, on references named `lock/zz-proof-*`, deleted afterwards — needs `POST`, `PATCH` and `DELETE` on `/git/refs`. **All three are denied by this session's proxy**, with the same 403 quoted above. There is no route around it and the proxy's guidance says not to look for one.

**Why this is not a formality.** The lock design rests on two claims about the API, and the spec tags both `[Likely — standard API behaviour; proved in step 4]`:

1. creating a reference that already exists is refused;
2. updating a reference with `force: false` is refused unless the update is a fast-forward.

I read GitHub's REST documentation fresh today rather than working from memory, which is what the spec's "Read first" asks for and what the red team's second pass found B02's first version had failed to do. The documentation **confirms the semantics of (2)**: `force` is a boolean, default `false`, described as *"Indicates whether to force the update or to make sure the update is a fast-forward update"*, and it says that leaving it out or setting it false guards against overwriting work. But it lists only the status codes `201/409/422` for create and `200/409/422` for update, and **states neither which code a duplicate create returns nor which code a refused non-fast-forward returns.** So the documented behaviour supports the design and does not pin the observable response.

**What step 4(i) does and does not prove.** The local backend in `test_lock.py` *emulates* those two properties: `git update-ref --stdin`'s `create` for (1), and for (2) a read, a `merge-base --is-ancestor` check and a compare-and-swap against the value just read. Those 40 races prove that **the lock protocol yields exactly one winner given a backend with those properties**. They do not prove GitHub has them. The emulation is test-side and unvalidated against the real thing — exactly the gap O-19 exists to name, and I am naming it rather than letting the local green stand in for it.

**The founder's decision, taken at about 20:01 UTC on 19 Nov:** build everything else, run step 4(i), and leave 4(ii) explicitly unproven with the status `halted` naming only that. He runs the 40 GitHub races by hand from a session with reference-write access, or B05 picks them up.

**What clearing it needs.** Nothing in this build changes. Run the two races against GitHub on `lock/zz-proof-*` references, confirm one winner in each of the 40 pairs, delete the references, and paste the count and one sample pair of API responses here. If either race shows two winners, or GitHub accepts a non-fast-forward update with `force: false`, then the spec's second Halt-if fires: the lock design is wrong and an alternative — a lock held as an issue assigned through the API — has to be proposed instead.

The pull request is still marked ready and the report is complete, so the review can proceed over everything that *is* finished; the halt is a flag on one named gap, not a reason to leave the rest unread.

Reviewer rule 3 makes this the reviewer's job, and it does it independently. I did it anyway, because a 39-row table that goes green on its first run is exactly the kind of thing that deserves to be distrusted, and because BLUEPRINT 2.5 says a check that has never been seen red proves nothing. **Twelve breaks, each reverted, each going red:**

**One of those twelve is a finding, not a formality.** Dropping the session id from the lock commit message produces **two winners** in the take-over race. Git commits are content-addressed: two sessions racing to take over the same stale lock build their commits on the same parent, with the same (empty) tree, so if their messages are identical the two commits are *the same object*, both updates trivially succeed, and both sessions believe they hold the lock. The session id in the message is the only thing making them distinct. This is written down because it is invisible from the code and a later build tidying that message would reintroduce it.

### One defect CI caught that every local run hid

Worth its own heading because it is the cleanest example in this build of CLAUDE.md rule 8 — *"tests green" is not "it works"*.

The lock races shell out to `git commit-tree`, which needs an author identity. This machine has a **global** git identity, so the 40 races passed locally every time I ran them. The CI runner has none, so run `44618675560`'s tests job failed: **10 failed, 261 passed**, every failure `LockError: Author identity unknown`. The test was quietly depending on ambient machine configuration.

Fixed by giving the throwaway bare repository an identity of its own, in the environment of every git call it makes as well as in its own config, so the test depends on nothing outside the repository it creates. **Verified against the real condition rather than assumed:** the whole suite re-run with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null`, which reproduces a runner with no git identity at all — 271 passed. ## One thing this build proves less than it looks

Beyond step 4(ii), which has its own section: **`facts.gather` is the least-tested thing here, and it is the part that touches the real world.** Its pure pieces are well covered — `halt_in_force`, `validate_status`, `_pull_requests`, `_checks` all have their own tests, including negative ones. The assembly around them has been exercised end to end exactly once, by the step 6 dry run, against a toy repository with GitHub stubbed. That single run is what found the `checks` bug, which is evidence both that the dry run is valuable and that one run is thin cover.

Concretely, these have never been exercised against the real repository: `_locks` parsing a real lock commit (no lock reference has ever existed), `_pr_state`'s review half against a real pull request, and `_halt_issues` against a real labelled issue. The decision logic for all three is tested; the wiring that fills them has only ever run against stubs. B04 drives this code for the first time in anger and B05 runs it unattended, which is where those gaps will show.

**One of these was worse than untested, and is now fixed rather than merely disclosed.** While writing this section I found that `_pr_state` read its review state from `_reviews` and `_needs_owner_review` keys that **nothing populated**, so the code-owner review state was always `None` — which would have made rows 28, 28b and 28c correct in `decide()` and unreachable through `gather()`. Deliver 2 asks in so many words for "pull requests for build and gate branches (open, merged, closed unmerged, **waiting on code-owner review**)", so this was a Deliver item half-built, not a gap in the spec. `_pull_requests` now fetches each open pull request's reviews and `_pr_state` reads them: the founder is the sole code owner, so "waiting on him" means he is a requested reviewer and has not yet approved, and only his latest verdict counts. Ten tests cover it, and three breaks confirm they bite — a `COMMENTED` review counting as a verdict, anyone's approval counting as his, and reviews being fetched for closed pull requests all go red.

That leaves the honest position: the review half of `_pr_state` is now implemented and unit-tested against stubs, and still unexercised against a real pull request.
