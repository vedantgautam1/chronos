## What now exists that didn't before

**Before today, anything with access to this repository could do anything to it.** There were no rules on `main` or on `v2-build`. One account — yours — did everything. Nothing stopped a bad change from going straight in.

**Now there is a second GitHub account that does the automated work, and it is genuinely fenced in.** Not "we told it not to" — GitHub itself refuses it. The automation cannot change a spec, cannot touch any file that is yours, cannot push straight to a branch, cannot force a branch backwards, cannot delete or rename one, and cannot change the rules that stop it. It cannot keep an approval you gave it if it pushes again afterwards. And when it posted five fake "all checks passed" marks on a commit where nothing had run, GitHub refused the merge anyway and said why: those marks did not come from the real test runner. Each of those is written down below with GitHub's exact words.

**Three things are honestly worse than hoped, and they are the part worth reading.**

The first: **the loop still cannot run by itself.** The lock — the "do not disturb" sign that stops two sessions doing the same job — cannot be put up from Anthropic's cloud, which is where a scheduled task runs. Worse, taking it down silently does nothing while reporting success, so a status report would tell you the sign came down when it is still hanging. That is one small file, and fixing it is a build of its own. Until then builds are run by hand from your Mac. **The three test runs this build was supposed to end with never happened**, so nothing here proves the loop works unattended, and this report does not claim it.

The second: **`main` is much less tested than `v2-build`.** Three of the four attacks aimed at `main` could not be run properly, because `main` still holds the old v1 code and cannot run the checks its own rules now demand. One of the four did work and passed. So `main`'s rule about fake checks is proven; `main`'s rules about approvals are not. Your spec already expected this to finish at the G1 gate.

The third: **the fence depends on a setting you can change with one click.** The automation cannot change your rules because the Claude app it works through has no admin permission. GitHub is currently asking you to widen that app's permissions. Approving the wrong one later would quietly remove a wall, with nothing in the repository changing to show it.

## Deviations from the spec

**Seven. None cleared in advance except the first, which the founder settled explicitly on 23 Nov.**

1. **Deliver 6 not done, and Deliver 5 half done.** A cloud session cannot take the lock. Put to the founder as a halt at step 0 on 20 Nov; on 23 Nov he chose to keep unattended operation as the goal, correct `lock.py` in its own build, and take Deliver 1–4 now. `lock.py` is outside this build's `touches`. The spending-limit half of Deliver 5 was done (a $20 monthly cap on usage credits, 23 Nov).
2. **The spec names two required checks that do not exist.** It asks for `guards` and `earlier-tests`; GitHub reports `guards (from the base commit's copy)` and `earlier-tests (the base's tests, this branch's package)` (`v2-guards.yml` lines 35 and 83). Requiring the spec's names would have blocked every pull request forever. The real names were used. **This is a spec defect, not a build defect.**
3. **A1, A2 and A3 could not be isolated.** Both framings are refused for the wrong reason: a `main`-based head cannot run the five required checks, and a `v2-build`-based head conflicts with `main` wholesale. The spec's "Not in scope" defers A1–A4 to G1, but its gate list still asks for A1–A9 refused for the named reason. **Those two cannot both hold.** A4 is the exception and was proven.
4. **A11's three per-step readings were lost and reconstructed.** The polling wrapper parsed `uv`'s deprecation warning as JSON. Rather than claim them, each step was re-established by pulling the real GitHub timelines for issues #47 and #48 and passing each separately to the loop's own `halt_in_force`. Real data, real function.
5. **The scheduled task could not be created switched off in one step.** No disabled option at creation; it existed `enabled: true` for 18 seconds with the next firing 21 minutes away, then was disabled and verified.
6. **The Mac ran the pre-rewrite attack script.** It found that `GH_TOKEN` governs `gh api` but not the Mac's git credential helper, and pointed git at the automation's token for that run. Net effect is **better** coverage: A5e was refused over both git and REST.
7. **Two throwaway branches were created and could not be deleted** from a cloud session (`lock/proxytest`, `doc/b05-deltest`). Both since removed. A permanent `__b05probe__` commit status remains on `b9c4f5d` from the first version of `measure-env.sh`; GitHub does not allow statuses to be deleted.
8. **Builder rule 7 cannot be met literally by a build of this shape.** It says to end on the commit carrying the code, with report, changelog and status in that same commit. This build's only code is two measurement scripts committed days earlier; its deliverable is a configuration on GitHub and the evidence that it bites. There is no final code change to attach the paperwork to. The rule's purpose is met — the closing commit carries `Chronos-Role: builder` and is the last builder commit, so the `roles` guard sees what it expects — and `head` is `null` for the usual reason. Flagged because a reviewer checking the rule literally will find it unmet, and that should be a deliberate note rather than a discovery.

**Design choices a reviewer should see stated:**

- Evidence lives in `docs/v2/build/probe/**`, inside `touches`, so it survives between rounds and is re-runnable rather than inherited.
- `status/B05.json` keeps a `halt_options` array after the halt cleared, as the record of what the founder decided. `head` is `null`, per builder rule 7.
- Attack pull requests were left open while the attacks ran so their refusals stay inspectable.

## What this build proves less than it looks

**It does not prove the loop works.** Nothing ran unattended. The scheduled task has never fired. B97, B98 and B99 do not exist. Every "wall" below is about GitHub refusing a merge, not about the loop doing its job.

**It barely tests `main`.** Five of the six walls are on `v2-build`. On `main` only A4 was isolated. `main` cannot currently run the checks its own ruleset requires, so **no pull request into `main` from a `main`-based branch can merge at all** today. The gate path (`v2-build` → `main`) is fine because its head carries the v2 workflows — evidenced by PR #41 reporting all seven checks — but that path has never actually been exercised.

**The walls rest on a permission set, not on anything in the repository.** A6 refuses because the Claude app lacks admin. That is one setting, changeable by approving a dialog, and GitHub is currently asking for exactly such an approval. No guard in this repository would notice.

**A4 is narrower than it reads.** It forged commit *statuses*. It did not forge a *check run*, a different API, and the app holds `checks: write`. That variant could not be tested: the proxy blocks it from cloud, and a user token cannot create check runs at all — only a GitHub App can. The pinning is by app identity, so it should refuse the same way, but that is reasoning, not measurement.

**A11 is a guard rail and nothing more.** The halt held three times, but only because `facts.halt_in_force` says so, and that script is run by the automation's own sessions. A session that skipped it would not be stopped. Its `halt_in_force` also walks the timeline in list order rather than by timestamp; issue #48's events came back inverted when the probe acted inside one second. The direction is fail-safe — a halt gets stickier, never lifted — and it cannot trigger at human timescales.

**The seam that is not tested:** `lock.py` ↔ the GitHub ref API in a *scheduled* session. Every lock measurement here was made from an interactive cloud session. A scheduled session is the same environment and should behave identically, but that is an inference.

**New traps for `BUILD_NOTES.md`:**

1. A cloud session can create and force-push a branch and **cannot delete one** by any route.
2. `POST /git/commits` is refused through the proxy as well as `/git/refs` — the lock fails one call earlier than previously recorded.
3. Cloud sessions follow Claude's GitHub connection; **Mac sessions use the local `gh` keychain**. They diverge after an identity switch, and `GH_TOKEN` does not govern the Mac's git credential helper.
4. Required-check names come from a job's `name:` override, not its key. Verify against real check runs, never the YAML.
5. `GET /rules/branches/<branch>` is the only reliable answer to "is this branch protected". A ruleset's own configuration can read perfect and apply to nothing.
6. GitHub answers **404, not 403**, when a token may not administer a resource.

**Spec defects:** the two wrong check names (deviation 2); and the contradiction between "Not in scope" deferring A1–A4 and the gate list requiring A1–A9 (deviation 3).

**Open questions for the founder:**

1. **`lock.py` needs its own spec.** Release cannot be a delete from cloud; `GitHubRefs.delete` must stop discarding its return code. This build must not design it.
2. **A second scheduled task exists** — "Chronos review watcher", off, created 17 Nov — which writes statuses without taking a lock. Delete or reconcile before either is switched on.
3. **`require_extra_approval_for_unattributed_changes`** came back `true` on `main` and `false` on `v2-build`. The spec names it nowhere. Adopt or turn off deliberately.
4. **`require_last_push_approval` on `v2-build`** is still off. The spec makes it conditional on A10 still passing with it on; that second A10 run has not been done.
5. **The Claude app's pending permissions request.** Not accepted during this build. Re-run A6 and A12 if it is.
