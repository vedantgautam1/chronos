## What now exists that didn't before

**Before this build, anything with access to this repository could do anything to it.** There were no rules on `main` or on `v2-build`. One account (yours) did everything, and nothing stopped a bad change going straight in.

**Now a second GitHub account does the automated work, and it is genuinely fenced in.** Not "we told it not to": GitHub itself refuses it. The automation cannot change a spec, cannot touch any file that is yours, cannot push straight to a branch, cannot force a branch backwards, cannot delete or rename one, and cannot change the rules that stop it. **It cannot get anything into `main` without your approval.** It tried three ways: merging its own pull request, pushing onto yours and approving it itself, and pushing again after you had approved. GitHub refused all three, each time for one reason only: *"New changes require approval from someone other than the last pusher."* It cannot keep an approval you gave once it pushes again afterwards. And when it posted five fake "all checks passed" marks on a commit where nothing had run, GitHub refused that merge too. **All nine attacks the spec says must be refused were refused**, each in GitHub's own words, quoted below.

**Three things are honestly worse than hoped, and they are the part worth reading.**

The first: **the loop still cannot run by itself.** The lock (the "do not disturb" sign that stops two sessions doing the same job) cannot be put up from Anthropic's cloud, which is where a scheduled task runs. Worse, taking it down silently does nothing while reporting success, so a status report would tell you the sign came down when it is still hanging. That is one small file, and fixing it is a build of its own. **The three test runs this build was supposed to end with never happened**, so nothing here proves the loop works unattended, and this report does not claim it.

The second: **on your Mac, Claude is you.** Claude Code on the Mac uses the Mac's own GitHub login, which is your account: the owner, the admin and the only code owner. Every wall above is a wall against the *automation* and lets *you* through, so a Mac session gets through too. Until the lock is fixed, builds run by hand on the Mac, so **those builds are protected only by our own scripts, not by GitHub.** The G1 gate has to choose: log the Mac's Claude Code in as the automation, or accept that in writing.

The third: **`main`'s automatic checks don't protect it yet.** A pull request into `main` can bring its own workflow, and GitHub then counts all five required checks as passed. What actually stops a bad merge into `main` today is the approval rule, and only that, until `main` gets its own list of code owners at G1.

One more thing, for you rather than about the build: **PR #37, this build's own branch, was merged into `v2-build` before any review.** It carried one of the build's two scripts. Merging a build before its review skips the one check that builds 1–5 have (deviation 9).

## What this build proves less than it looks

**It does not prove the loop works.** Nothing ran unattended. The scheduled task has never fired. B97, B98 and B99 do not exist. Every wall below is about GitHub refusing a merge or a write, not about the loop doing its job.

**Every wall exempts the founder's account, and a Mac session is the founder's account.** The build measured that a Claude Code session on the Mac uses the local `gh` login, `vedantgautam1`: owner, admin, only code owner (`probe/B05-environment-measurements.md` §7c-bis). A Mac session can approve as code owner, so it can merge founder-owned paths on `v2-build`, and its approval plus the automation's push satisfies `main`'s approval rule. Until `lock.py` is fixed, by-hand builds run on the Mac. That is the situation the spec's "Why" says B05 exists to end. HANDBOOK §2 now says so.

**`main` is walled by its approval rules alone.** A1–A3 prove those rules refuse the automation acting alone, three ways. `main`'s required checks are **not** part of the wall before G1: PRs #51, #54 and #55 each got all five contexts green from a workflow the pull request itself brought. And for 21 seconds during A3, between the founder's approval and the automation's push, #55 was mergeable into `main`. That is the rule working as designed (he had approved that commit), but it is the shape of the wall: one approval from the founder's account, on the exact commit, is the whole of it.

**The gate path is not clean today.** `v2-build` → `main` would conflict in two files, `docs/v2/CHANGELOG.md` and `docs/v2/CHRONOS_V2.md`, because `main` took seven commits of spec work after 17 Nov (merge base `3500d52`; 2 of 106 differing files; `git merge-tree --write-tree origin/main origin/v2-build`). Not B05's to fix; G1's move needs it resolved first, and `CHRONOS_V2.md` is founder-owned.

**A4 is narrower than it reads.** Forged **statuses**: a wall on both branches. Forged **checks**: a wall on `v2-build`, where `.github/` is founder-owned (A9, #42); **not** on `main` until `CODEOWNERS` reaches it at G1. A pull request that brings its own workflow gets real GitHub Actions check runs under the required names, and the pin to app 15368 accepts them. The Claude app's `checks: write` is a secondary edge, and untested.

**A6 measures the automation's collaborator role, not the Claude app's permissions.** A6 ran on the Mac with a classic token, and the app is not in that path. Its refusal meets the spec's bar on its own evidence: the same token lists ruleset 27930220, gets `404` on `PUT` to that id, and reads the id back unchanged. For cloud sessions, GitHub's documentation says a user access token has only the permissions both the user and the app have, so widening the app would not let a collaborator change a ruleset *[Likely: documentation, not measured]*. The app's pending permissions request still deserves a deliberate yes or no, but it is not the cliff round 1 described. What would break A6 is a session acting as the founder (above).

**A11 is a guard rail and nothing more.** The halt held three times, and again in review r1's clean re-run, but only because `facts.halt_in_force` says so, and that script is run by the automation's own sessions. A session that skipped it would not be stopped. *(Round 1 also said `halt_in_force` walks the timeline in list order rather than by timestamp. That implied sorting would change #48's result. It would not: GitHub's own timestamps on #48 are inverted, `unlabeled` 20:05:13Z before `labeled` 20:05:14Z, so the two orders agree. Removed.)*

**A12 is narrower than "exactly two identities".** Two collaborators, read from the Mac. Not covered: **deploy keys**, which can push code and which neither identity could read; the **Claude app acting as itself** through an installation token, which would be a third approver if anything ever used it that way (that it "acts as those accounts" is inferred from what was observed *[Likely]*); and the **bypass list**, inferred empty from `current_user_can_bypass: never`, which speaks only for the account asking. Only the founder's screen can confirm the last. GitHub Actions as an approver is closed off: review r1 got `"GitHub Actions is not permitted to approve pull requests."` from a workflow token.

**Two Deliver 2 / Deliver 5 settings are configured but not least-privilege or not read back.** "Default workflow token permissions: read" has not been read back by anyone (`/actions/permissions` is blocked from cloud). The build-loop task carries **seven connectors**, including Gmail and Google Drive, and `permission_mode: auto`; the spec names neither, and an unattended build loop needs none of them.

**The seam that is not tested:** `lock.py` ↔ the GitHub ref API in a *scheduled* session. Every lock measurement here was made from an interactive cloud session. A scheduled session is the same environment and should behave identically, but that is an inference.
